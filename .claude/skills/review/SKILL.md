# review（変更を確認する ＝ 独立した確認の経路）

作る側と確かめる側を分けるための手順。実装した本人・実装と同じ文脈のエージェントは、この確認を自分で行わない。
別の立場（別セッション・別エージェント、チームなら別の人）から、差分だけを見て確かめる。

## 手順
1. 作った人とは別の立場で（先入観なしに）、変更点（差分）だけを見る。
2. 正しさと、SPEC の受け入れ基準からのずれを探す。あら探しの目で見る。
3. 指摘は「正しさ」と「はっきり書かれた要件に関わるずれ」に絞る（好みや細かい体裁で範囲を広げない）。
4. 最後に判定を1つ出す：**問題なし** か **重大な問題あり（ブロック）**。重大とは、正しさを損なう・受け入れ基準を満たさない類の問題。

## ドキュメント観点（文書の変更を見るとき）
機械の検査（doc_standards＝孤立・凡例・用語集・導入の有無）は verify が担保する。レビューは機械が判定できない質を、読者の立場で問う（正本は DEC-0019）：
- 初見で理解できるか：その文書だけを、前提知識なしに読んで何の話か分かるか。導入（lede）は実際に平易か。
- 全体像→詳細の順が本文の流れとして実際に成り立っているか（見出しの並びだけで満足しない）。
- 過不足がないか：読者が目的を果たすのに不要な装飾・重複が無いか。必要な事実が欠けて・弱められていないか。
- 標準用語か：造語を新しく増やしていないか。内部用語は初出で定義するか用語集（docs/glossary.md）へリンクしているか。
- Diátaxis の種別（Tutorial／How-to／Reference／Explanation）として正しいか・1 文書に混ざっていないか。

## 完了との関係
- 完了は、客観的な自動検証（`uv run verify`）の成功で確定する。レビューが主観で合否を付けて完了にするのではない。
- ただし、この確認が**重大な問題**を指摘している間は完了にしない（マージをブロックする）。完了は「検証コマンドの成功」と「重大な問題でブロックされていないこと」の両方がそろって初めて確定する。
- 好み・細かい体裁の指摘は、完了をブロックしない（別タスクや任意の改善として扱う）。

## してはいけないこと
- 作った本人が自分で合否を判断する（作る側と確かめる側を分ける）。
- 主観だけで重大と判定する（重大かどうかは、正しさ・受け入れ基準に照らして根拠を示す）。
