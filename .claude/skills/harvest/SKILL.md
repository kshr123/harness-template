# harvest（振り返って次に活かす）

気づきを durable な資産へルール化し、後戻りさせない（進化の歯止め）。全体像は `docs/method.md` C 節。

## 手順
1. 気づき（工夫・使いにくかった点）を `docs/learnings.md` に記録する（1 件＝1 項目・なぜも・状態: 記録のみ）。
2. 既存の learnings を見て、一般性・再発が見えた項目があれば落とし先を 1 つ選ぶ（判定表は method.md C 節：機械検査／抽象／スキル／規約）。
3. ルール化するルールは、**先に「違反すると失敗する検査」を足してから**直す（テスト先行と同じ・退行を機械で止める）。検査にできないものは AGENTS に 1 行＋「（レビュー観点）」の印。
4. ルール化したら learnings の「状態」を「ルール化済み（先例として当面残す）」に更新し、次の見直しで消す（正本が移ったので）。使われていないスキルの統廃合を検討する。逆に、**使える状態になっていない部品**（カタログに載らない・どのスキルからも導かれない `src/` の再利用部品）が無いかも見る（あれば使える状態にする作業を 1 タスク起こす）。あわせて**スキル・規約の記述が現在のルールと矛盾していないか**を 1 点見る（撤去した仕組みを古いスキルがまだ指していないか。正本は AGENTS / method / 検査コード側・スキルは追随する）。**仕組み・識別子を撤回したときは、その名前を横断検索して残骸が資産（src・docs・skills・templates）に残っていないか確かめる**（撤回した名前は撤回時に有限に確定する＝撤回という一手の中で 1 度 grep すれば足り、常時走らせる検査には載せない）。
5. ルール化の結果（検査・抽象・スキル・規約・レジストリの住人）で、一般的だと見えたものは本体（テンプレート）へ**還流**する。単位は「本体領域だけに触る 1 コミット」（案件領域の変更と混ぜない＝コミット境界＝資産境界）。それを cherry-pick か harness-template への PR で戻す。**回数で待たない**（「2 案件で役立ったら」ではなく、一般性が見えた時点で候補にする＝method.md C 節）。案件のエージェントは候補の PR を起こすところまで。採否はテンプレート側の verify 緑＋別文脈のレビューが決める（判断者は既定でオーナー）。手順の正本は `docs/template-copy.md` の還流の節。まだ戻していない本体領域の変更は git で洗える（還流候補＝台帳を作らず git から導く。pathspec の正本は `docs/template-copy.md` 5 節）：`git log --oneline upstream/main..HEAD -- src tests .claude/skills templates AGENTS.md CLAUDE.md checks.toml .pre-commit-config.yaml .github docs ':(exclude)docs/charter.md' ':(exclude)docs/learnings.md' ':(exclude)docs/requirements' ':(exclude)docs/data'`。**learnings 自体は還流しない**（案件領域＝白紙化で消える観察の材料。運ぶのはルール化の結果）。

## してはいけないこと
- リポジトリや履歴が既に記録することは書かない。1 回きりの工夫を基盤に入れない。
- 正本を 2 か所に書かない（他の層はリンクで参照）。古くなった記録は消す（ためこまない）。
