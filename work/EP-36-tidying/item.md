## 記録：層の再編の指摘（着手は保留）
- core には性質の違う 2 種が同居している。**メタ層**（リポジトリ自身の完了・検証・進捗を定義。
  プロファイル 0 個でも存在する）と、**相互運用契約**（複数のプロファイルが合意しないと、値・記録・判定が
  食い違って事故になるもの）。`docs/core.md` は表を 2 つに割ってこれを自白している。
- 「消費者が 2 つ以上なら core へ」は**配置の基準ではなく昇格タイミングの経験則**。配置の基準は
  「2 つのプロファイルが別々に持つと、観測可能な事故になるか」。
- プロファイル 4 つは同種でない。`ds`・`agent` は**領域**（何を作るか）、`serve`・`ops` は**段階**
  （ライフサイクルのどこか）。`serve` は `ds` を import し、私有関数 `ds.cv._predict` に越境している。
  一方 `agent` は配信を `agent/app.py` として自前で持ち「`harness.serve` は import しない」と明記した。
  **コード自身が「段階は領域の中に置く」と結論している**のに、`serve` だけが対等を詐称している。
- 昇格規則が不均一に適用された。`gates` は ds/agent の重複を理由に中核へ昇格したのに、同じ状況の
  `leaderboard`（ds/cli・agent/cli が両方使う）と `eval.passes`（両方に同名重複）は放置。
  原理でなく作業順（EP-22 が gates だけ触った）の産物。
