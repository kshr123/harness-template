# EP-35 黙って間違った答えを出す経路を塞ぐ

## なぜ独立した束にするか
目的（案件を重ねるほど強くなる）で測ると、欠陥は 2 種類に分かれる。

- **成果物が黙って間違う**（直結）：リークした指標で出荷する・劣る版を配信する・列を取り違える。
- **機構の健全性**（間接）：検査が空振りする・文書が腐る・層の境界が乱れる。

このエピックは前者だけを集める。**良い指標つきで出荷されるリーク**が最悪の形で、
本番で崩壊するまで誰も気づかない。

## 実測で確認した経路
1. **`cluster` / `anomaly_score` 列の黙った上書き**（再現済み）。入力に同名列があると警告なく置き換わる。
   さらに `columns` 省略時は「数値列すべて」なので、**正解ラベルが特徴としてクラスタリングにも使われる**。
   polars は immutable なのでディスク上のデータは壊れないが、返り値のレポートが黙って間違う。
2. **`run_experiment` が `group_by` を受け取らない**。`cv.make_folds` は `GroupKFold` を選べるのに、
   実験の正規経路から到達できない。同じ実体が複数行に現れるデータで group を指定せずに交差検証すると
   リークし、**リークした指標は「良い結果」に見える**。
3. **`schema.validate` は宣言外の列を検査しない**。目的変数のコピーが features テーブルに同乗して保存される。

## 3 番目の直し方についての訂正（独立レビュー 2026-07-10）
当初「宣言外の列を既定 error にする」と設計したが、これは**効かない**。
one-hot 等のエンコーダ由来の列は値に依存して動的に増えるので、特徴量テーブルの全列宣言は実務的に不可能で、
そのテーブルだけ `allow_extra: true` にすることになる。**標的（目的変数の同乗）が起きる場所でちょうど検査が無効化される。**

正しい形は、発生源が有限に列挙できるものを塞ぐこと：**目的変数の列名・ID 列名が特徴量テーブルに現れたら
`ValueError`**（宣言済みの名前との照合なので、集合は構文から導ける）。

なお EDA の中間テーブルは `store.save`（`validate` の唯一の呼び手）を通らないので、落ちる心配は無い（実測）。

## 却下した対策（L-017 の適用記録）
- **`store.save` の全層で `overwrite=True` を明示必須にする**：split 層は既に再書き込みを拒否している。
  他の層の反復再導出は正常運用なので、雛形が `overwrite=True` を定数で書くだけになり検査が形骸化する。
