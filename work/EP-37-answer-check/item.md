# EP-37 答え合わせ（配信予測×実績）＝黙った劣化に気づく経路

## なぜ作るか（目的への直接の寄与）
最上位の目的は「案件を重ねるほど強くなること」。その第 1 条件は**成果物が黙って間違っていないこと**。
既存の配信後の仕組みは「気づく → 特定する → 規則にする」の閉ループを持つが、**気づく**の部分が
分布監視（psi/drift）＝**入力のずれの代理**しか無かった。入力の分布が安定したまま現実の正解率だけが
崩れた champion は、代理では見えない。「誤って間違っても気づかない」なら、いくら案件を重ねても強くならない。

この穴（実測での答え合わせが存在しない・かつどこにも「やらない」と宣言されていない＝L-022 違反）を塞ぐ。
特定（fingerprint・昇格時 metrics・切り戻し）と規則化（`--file-issue`→作業単位）は既に在るので、
足りない 1 本＝**後から届く実績と配信予測の突き合わせ**だけを、既存部品の合成で足す。

## 設計の要点（なぜこの形か）
- **門番にしない**（drift 監視と同型）。実測劣化は band で人が読む・exit code に載せない。閾値の判断は人。
- **既存部品の合成のみ**：契約は `serve/runtime.py` の PREDICTION_LOG_FIELDS（serve は import しない＝境界）、
  指標は `ds/eval` の evaluate 系（sklearn 素通し）、起票は `issues.py` の既存 API。新しい監視ロジックを作らない。
- **L-017 との関係**：これは「自分が作りうる欠陥の検出器」ではない。検出するのは**世界が作る劣化**
  （現実が昇格時の約束から乖離する）であって、自作の欠陥の発生源（リーク・列取り違え等）は EP-35/EP-33 で
  既に塞いだ。世界の変化は発生源で塞げない種類なので、実測での答え合わせが正しい対処。
- **保証しないことを書く**（L-022）：正解ラベルが決して届かない案件では成立しない。docs/ops.md に明記。
