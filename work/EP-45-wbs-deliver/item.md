# EP-45 クライアントに見せる WBS・ガントを、作業単位の木の生成ビューとして出す

コンサル層のバックボーン第 3 段（EP-43 で日程フィールド、EP-44 で要求→要件のトレースを入れた続き）。
クライアントと計画を合意し、定例で進捗を報告し、最終報告で計画対実績を出すための WBS を載せる。

## 設計の核（なぜこの形か）

**WBS はデータではなくビュー。日程の正本は `work/` の木ひとつ。**

WBS 専用の正本（階層と日程を持つ別ファイル）を作る案を検討して捨てた。EP-43 で Item に
`start`/`due`/`effort_days`/`milestone` を入れた以上、WBS 側に階層と日程の「枠」を持たせると同じ事実を
2 回エンコードすることになり、二重台帳そのものになる。乖離を包含検査で捕まえるのは、矛盾を作っておいて
絆創膏を貼る形。**矛盾の置き場を消す**（保証 (a)）。

したがって：

- 階層 … `work/` のフォルダ構造（「親はフォルダ」の既存原則）。WBS 側に入れ子を持たない。
- 予定日・工数・節目 … Item の frontmatter（EP-43 の既存フィールド）。
- 状態・実績 … `status` と `created`/`closed` から導出。
- WBS 番号・営業日数・進捗率・親のロールアップ … **フィールドとして存在しない**（保存できない）。
- 案件固有の上書き `docs/wbs.yaml` … カレンダー（国・非稼働日・振替出勤）、顧客向けの節構成と表示順、
  `work/` に置けない手動行（クライアント承認待ち・定例会議など）**だけ**。数十行に収まる。

## 生成物と編集面

**不変条件は「正本 1 つ・編集面 1 つ」であって「出力形式 1 つ」ではない**（STATUS.md・docs/core.md の
自動生成節と同じ形）。既定の成果物は自己完結 HTML 1 つだけ。Excel は openpyxl が入っている案件でだけ
生える枝（`FORMATS`/`MODELS` と同じ条件登録）＝既定で 2 つ並ばない。クライアントが編集した Excel の
再取込は作らない（変更要望は要求層 DEM で受ける）。

編集はローカルの編集サーバ（`uv run wbs`）とテキスト直編集の 2 経路だが、書き込み先はどちらも同じ正本。
編集サーバの保存は frontmatter の対象キーの**行置換**（`init_project.set_profiles` と同じ作法）なので、
差分は 1 単位あたり 1〜4 行に収まり、差分だけを見る独立レビューが成り立つ。

## 分解

- T-0245 … 骨組み（deliver プロファイル・上書きスキーマ・営業日・木との結合と導出・静的 HTML 出力・`wbs_lint`）
- T-0246 … 提出物の体裁（印刷・由来の刻印・未コミット時の拒否・下書き透かし・折りたたみ）
- T-0247 … 編集サーバ（フォーム編集・保存の競合検出・行置換の書き戻し）
- T-0248 … 合意版との差（git 参照の比較・変更を入れたコミットの提示）
- T-0249 … Excel の枝（条件登録）
- T-0250 … スキルと導線の仕上げ

検査（`wbs_lint`）は骨組みと同じタスクに入れた。参照が壊れた状態・親と子で日程が食い違う状態を通す期間を
作らないため（後から足す検査は、その間に書かれたものを既定で通してしまう）。

## やらないこと（形式だけで価値の無いもの）

アーンドバリュー（EV/PV/AC）、クリティカルパス計算とフロート、資源平準化・山積み、FS 以外の依存種別と
リード/ラグ、%完了の手入力、共同編集、クライアントが編集したファイルの再取込、バーを掴んで動かす編集
（バニラ JS で営業日スナップと依存の玉突きを書くと最もテストできない塊になる。セル編集で要求は満たせる）。
