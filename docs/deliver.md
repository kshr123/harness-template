# deliver — クライアントに見せる WBS とスケジュール（ガント）

案件の計画をクライアントと合意し、定例会議で進捗を報告し、最終報告で計画と実績を並べるための
WBS（Work Breakdown Structure＝作業を分解した一覧）とガント（工程を横棒で表した図）を出すプロファイル。
コンサル案件で顧客に提出する人と、その提出物がどの正本から出ているかを確かめたい人が読む Reference。

実装は `src/harness/deliver/`。場面ごとの作業手順（提案・定例・引き直し・最終報告）は
`.claude/skills/wbs/SKILL.md`。案件を始めるときの上書きの雛形は `.harness/templates/wbs.yaml`。

## 考え方（これだけは先に読む）

**WBS はデータではなくビュー。日程の正本は `work/` の作業単位の木ひとつ。**

WBS 専用のファイルに階層と日程を持たせると、`work/` の frontmatter と同じ事実を 2 回書くことになり、
必ずどちらかが古くなる。だからこのプロファイルは木を顧客向けに射影するだけで、日程を保存しない。

| 情報 | どこにあるか |
| --- | --- |
| 階層 | `work/` のフォルダ構造（親はフォルダ） |
| 予定開始・予定終了・見積り工数・マイルストーン | 作業単位の frontmatter（`start`・`due`・`effort_days`・`milestone`） |
| 状態 | 作業単位の `status` |
| 実績開始・実績終了 | 作業単位の `created`・`closed` から導出（未着手の行には実績開始を出さない） |
| WBS 番号・営業日数・進捗・親の日程 | **どこにも無い**（毎回導出する。書く欄が存在しない） |
| 担当・チーム | 作業単位の `owner`・`team`（名簿は `docs/wbs.yaml` の `members`・`teams`） |
| 暦・顧客向けの節構成・手動行・名簿 | `docs/wbs.yaml`（案件固有の上書き。数十行） |

導出の規則は `wbs.py` の冒頭にまとめてある（親の日程は子の最小・最大、進捗は末端の done 数 ÷ 末端の総数、
遅れは終了予定が基準日より前でまだ done でないこと）。営業日の数え方は `calendar.py`（両端を含む）。

## 使い方（How-to）

```
uv sync --extra deliver
uv run wbs edit [--port <番号>] [--today YYYY-MM-DD] [--idle-minutes 60] [--root <プロジェクトの根>]
uv run wbs export [--out <出力先>] [--format html] [--today YYYY-MM-DD] [--at <合意した時点>] [--draft]
uv run wbs diff <合意した時点> [--today YYYY-MM-DD] [--root <プロジェクトの根>]
uv run wbs formats
uv run wbs lint [--today YYYY-MM-DD]
```

- `uv run wbs edit` … 手元のブラウザで見ながら直す。表示された `http://127.0.0.1:<番号>/` を開き、
  セルをクリックして編集（Enter で保存・Esc で取り消し）。
- `uv run wbs export` … 自己完結の HTML を 1 ファイル出す（既定 `artifacts/wbs/WBS.html`）。外部リソースを
  読まないので、そのままクライアントへ送れる。ブラウザの印刷から PDF にできる（A3 横・見出しは各ページに再掲）。
- `uv run wbs diff <合意した時点>` … 合意した計画といまの計画の差を並べる（下の節）。
- `uv run wbs formats` … 出せる形式の一覧（入れていない依存の形式はここに出ない）。
- `uv run wbs lint` … `uv run verify` が回すのと同じ WBS の検査だけを単体で走らせる。

**出力を拒否する場合**（既定を不合格側に置く）：

- 検査に失敗する状態のとき（間違った工程表を良い見た目で渡さない）。
- 日程を持つ作業単位が 1 件も無いとき（空の工程表を黙って渡さない）。
- **WBS の入力**（`work/` と `docs/wbs.yaml`）に未コミットの変更があるとき（生成物に刻むコミットが実際の
  中身と食い違う＝由来が嘘になる）。作業ツリー全体は見ない＝生成物やメモを置いただけで拒否されない。
  定例の直前に 1 行直してすぐ出す実務のために `--draft` を残してあるが、そのときは生成物に「下書き」と出る。

## 見た目の決まり（`render.py` の `_STYLE`）

**色は 3 色まで（白・黒・青）＋警告の 1 色（赤）。** 濃さは変えてよいので、黒は 5 段・青は 3 段・赤は 2 段で作る。

- **＋1 色を赤にした理由**：赤は「遅れ」だけに使う（読み落とすと実害が出るのは遅れだけ）。**ガントの棒は
  1 色（青）**にして状態で色を分けない＝状態は行の側で示す（棒と行で二重に持たない）。遅れは表の赤い日付と
  行の面・今日の線で分かる。
- 明るい地・暗い地の両方を持ち、本文の文字は対比 4.5 以上、図形は 3 以上を満たす。白黒で刷っても状態の
  強さの順（遅れ＞進行中＞…＞完了）が保たれるように、面・文字の濃さ・左バーで表す。
- **罫線は重みを分ける**：弱（行の区切り・日の格子）／中（週の格子）／強（見出しの下端・月の格子・貼り付く列の
  右）／最強の 2px（**左の表とガントの領域の境目**＝いちばん濃い縦罫）。すべて同じ太さだと表計算の初期状態に見える。
- **左の表とガントは別の領域**として 3 重に割る：ガント専用の淡い地色（`--canvas`）・最も濃い 2px の縦罫・
  時間の格子（左はセルの格子、右は時間の図）。**状態の行色はガントに入れない**＝棒・格子・今日線は常に無地の
  キャンバスに載り、図が濁らない。
- **状態→視覚の強さは「意味の順」に割り当てる**（今どこを・誰がやっているか＝進行中と、遅れはどこか、が
  工程表で最初に読みたい情報）。**面（ベタ塗り）はページ最強の資源なので遅れだけに使う**。完了は面を敷かず
  文字だけ灰に退け、棒も淡くする（済んだ話は地に沈める＝完了がかえって目立つのを避ける）。進行中・確認中・
  停止は**左端 3px の縦バー**（進行中＝濃青／確認中＝淡青／停止＝黒）と状態語の強調で「今ここ」を積極的に示す。
  遅れはこれらに重なると赤い左バーと淡赤の面が勝つ。未着手は無印（白）。
- **整列**（デザインの 4 原則：整列・反復・近接・強調）：文字は左・数値と日付は右（見出しも中身に合わせる）・
  まとまり見出しは中央。時間軸は全段「区切り線の右・左余白 4px・左揃え」でそろえる（曜日も）。数字は
  桁をそろえる（tabular-nums）。番号（No.）は字下げしない（番号そのもの＋作業名の字下げ＋フェーズの面で
  階層は分かる）。同じ役割は同じ値（フォント・角丸・罫線の重み）を繰り返す。
- 行の縞は入れない（折りたたむと偶奇が崩れるため）。代わりに画面では行にかざしたときだけ地色を変える。
- **列は意味のまとまりで括る**：見出しを 2 段にし、上の段に「作業／予定／実績」を置く。まとまりの先頭には
  強い縦罫を引く（どこまでが予定でどこからが実績かを、列名を読まずに分けられる）。ガントの見出しは 2 段を
  ぶちぬくので、時間軸の 2 段と高さが揃う。
- **チーム・担当の列は消せる**（見出しの「列」の並び。案件によってはどちらも無い）。消すとまとまりの見出しの
  幅も数え直す。
- **終わった行には面を敷かない**（文字だけ灰に退ける）。面は遅れ専用＝残っている作業と遅れに目が行く。
- 時間軸の日付は区間の**左**に寄せる（線の右すぐ＝その区間の始まりの日、と読める）。短すぎて文字が切れる
  区間にはラベルを出さない。
- 見出し行は縦にスクロールしても固定する（表領域に高さを与え、その中でスクロール。印刷では解除）。
- 作業単位の ID（`EP-`・`T-`・`W-`）は閲覧では出さない（クライアントに関係ない。編集の参照用に属性では持つ）。
- クライアント向けに「未日程」の一覧は出さない（日程の無い行はガントが空なので見れば分かる）。
- 非稼働日の帯は敷かない（各週の右に灰色が並んで棒より目立つため）。週の区切りは格子線、営業日は「日数」の列で分かる。

## 提出物の体裁と由来

- **折りたたみ** … 親の行の WBS 番号の横の取っ手で畳める。見出しに「全部閉じる／全部展開」もある。畳んだ行は**隠れるだけで本文から消えない**ので、
  印刷では CSS が必ず戻す（畳んだまま刷って白紙のフェーズを渡す事故が、そもそも起こらない形にしてある）。
- **時間軸** … 見出しの右の「月／週／日」で切り替える。月・週は 2 段（上＝大きい単位・下＝選んだ単位）、
  **日は 3 段**（年月・日にち・曜日／土日は薄く）。月＝`2026年`／`8月`、週＝`2026年8月`／`8/3w`、
  日＝`2026年8月`／`1 2 3 …`／`土 日 月 …`。
- **粒度ごとに幅が変わる** … 月は狭く・日は広い（1 日あたりの幅を単位ごとに決める）。粗い単位に切り替える
  ＝情報量を落とすと、ガントも短くなる（表全体が横に詰まる）。
  文字は区間の**真ん中**に置く（線の右に寄せると、どの線の分か読めない）。「自動」という状態は持たない
  （自動は初期値の決め方であって、利用者が選ぶ状態ではない）。1 日あたりの幅を変えるだけなので、棒も格子も
  同じ表の中で伸び縮みし、行と棒がずれない（表ごと横にスクロールする）。紙では必ず全期間を収める。
- **期間と年** … 見出しに全体の期間を年月日で出し、時間軸の目盛は先頭と年が変わるところに年を付ける
  （毎回出すと重なって読めない／出さないと何年の話か分からない、の間を取る）。
- **完了した行**は落ち着かせる（取り消し線は付けない＝実績の日付は読ませたい）。
- **ガントの棒は 1 色（青）のベタ塗り**。予定・完了・遅れを色で分けない（状態は行の側で示す）。
  まとめの行（子を持つ単位）も普通の棒で、子全体の期間を覆う（階層は番号・作業名の字下げ・フェーズの面で分かる）。
  完了した行の棒だけは同じ色を淡くする（済んだ話を地に沈める）。
- 作業名は frontmatter の `title` があればそれ、無ければ**本文の見出し**（`# <ID> タイトル`）から ID を除いて
  拾う（title を書かない案件でも名前が ID にならない）。
- **引き伸ばす図形に文字と点を置かない** … 軸の日付・マイルストーンの印は、SVG でなく割合の位置に重ねる要素で描く
  （`preserveAspectRatio="none"` の図形は、列幅に応じて中身が横に潰れる／伸びる）。線には
  `vector-effect="non-scaling-stroke"` を付けて太らせない。
- **印刷** … A3 横。時間軸の見出しは各ページに再掲され、行の途中で改ページしない。配色は画面が明暗どちらでも、
  印刷は常に紙の版に固定する。ブラウザの印刷から PDF にする。
- **由来の刻印**（`stamp.py`）… 見出しに「コミット・生成日時・内容の指紋」を出す。内容の指紋は表に出ている
  値そのものから作るので、コミットが同じでも中身が違う／コミットが違っても中身は同じ、を見分けられる。
  git が無い場所ではコミットを「不明」にして拒否はしない（git を前提にしない）。

## 編集（`uv run wbs edit`）

**閲覧と編集は同じ画面**（`render.py` の同じ描き方）。違うのは、直せる欄に書き戻し先の目印が付くことと、
保存の口があることだけ。ファイルに書き出した生成物には保存の口が無いので、渡した先で編集はできない。

**書き込み先は正本ひとつ。** 作業単位の値は `work/` の frontmatter へ、手動行の値は `docs/wbs.yaml` へ、
**そのキーの行だけを置き換えて**書き戻す（`editor.py`）。ファイル全体を書き出し直さないので、コメント・並び・
引用符がそのまま残り、差分は 1 か所あたり 1 行に収まる＝差分だけを見る独立レビューが成り立つ。

直せる欄は決め打ちの一覧だけ：作業単位は表題・状態・担当・予定開始・予定終了・見積り工数、手動行は
名前・状態・チーム・予定開始・予定終了・見積り工数。**導出される値（WBS 番号・日数・進捗・親の日程）には
編集の口が無い**ので、画面から矛盾を入力できない。親の行は表題だけ直せる（日程・状態は子から導くため）。

**チーム・担当は名簿から選ぶ**：`docs/wbs.yaml` の `teams`・`members` が案件の名簿で、画面ではそこから
選ぶ（毎回打つと表記ゆれが起きる＝同じ人が別人として並ぶ）。名簿に無い名前を入れる口も残してあり、
入れると**その名簿にも足される**（選ぶ先と実際に使われている名前がずれない）。名簿への追記も 1 行だけの
書き換えで、書き方（1 行の並び・箇条書き）は人が書いたものに合わせる。

**右クリックは列ごとに変わる**。クリック＝値の編集（唯一の編集面）、右クリック＝一発コマンド（メニューから
編集ボックスは開かない）と役割を 1 本に分ける。だから二重の編集導線が消え、「メニューに出るもの＝即実行」が
全列で成り立つ。
- **作業（名前）列**＝構造操作の唯一の置き場：上／下／子に追加・マイルストーンを下に追加（◆）・削除。改名は
  クリックでできるのでメニューには出さない。足す先は行が持っている（この下＝自分がフォルダの単位のとき／
  同じ階層＝いちばん近い親のフォルダの単位）ので、画面側で組み立て直さない。最上位に足すのは Lv1 の行の
  「上に／下に追加」で足りる（専用ボタンは持たない）。
- **状態列**＝状態を一発で設定（現在値は ✓ 付きで無効）。**日付列**＝今日にする／クリア。**チーム・担当列**＝クリア。
  いずれも同じ編集セルへの保存を呼ぶ（競合検出も同じ経路）。選択肢は日本語で出し、送るのは正本の値。
- **上位の行の状態列**＝「配下をすべて〈状態〉にする」（`POST /cascade`）。上位の行の状態は子から導く値なので
  その行自体には持たせられない（持たせると二重台帳になる）。まとめて変えるときも**書くのは末端の正本だけ**で、
  上位の表示は導出で自然に追随する。末端をまとめて書いたあとに検査を 1 度だけ行い、増えた指摘があれば
  全部書き戻して断る（部分適用しない）。1 操作＝1 手なので Ctrl+Z でまとめて戻る。
- **導出列**（WBS 番号・日数・実績・進捗・ガント）＝無反応にせず「何から導かれるか」を説明する（無反応は
  故障に見える＝正本の在り処を毎回教える）。作業列以外の末尾には「行の追加・削除は『作業』列で」の道しるべを置く。

**作業を足す**（`adder.py`）：作業列の右クリックから、対象の上／下／子に 1 つ足す。ID は既存の最大＋1（再利用しない）。
ファイル 1 つで表した軽い単位の下には置けない（親はフォルダで表すため。分解してフォルダにするのは人の作業）。
**未分解の単位を分解すると、その単位の日程・工数は最初の子へ移る**：子ができた瞬間、親の日程は子から導く値に
なるので、宣言を残すと検査に失敗する。分解という操作の意味に合わせて移すことで、1 手で分解できて不変条件も
保たれる。足した結果として検査に落ちる場合は、足したものを消して理由を返す。

**行を消す**（`remover.py`）：右クリックの「消す」。消すのは正本だけで、手動行のときは上書きファイルの
その塊と、**それを指している節の項目も一緒に**取る（片方だけ残すと参照切れになる）。配下を持つ単位は
まとめて消さない（何が消えるか画面から見えないため）。先に配下を消す。

書き込む口（直す・足す・消す）はどれも、**作業単位の検査（`pm.lint`）と WBS の検査の両方**を書く前後で
見比べ、**増えた指摘だけ**を拒否の理由にする。WBS の検査だけを見ると、参照が切れた `depends_on` のような
作業単位の側の壊れ方を通してしまう。

**全部閉じる／全部展開**は見出しの操作にある（閲覧でも編集でも使える。印刷には出さない）。

保存に成功すると画面を作り直す。日数・ロールアップ・進捗・遅れは導出値で、1 か所直すと他の行の値も動く。
画面側で計算をやり直すと計算が 2 か所になるので、導出はサーバの 1 か所に置いたまま毎回まるごと描き直す。

安全のために 3 つ重ねる（`editor.py`・`server.py`）：

1. **競合検出** … 画面を開いた時点のファイルの指紋を保存時に突き合わせ、違えば書かずに拒否する
   （別の手＝エディタ・エージェント・git の操作で正本が動いていたのに、古い値で上書きするのを止める）。
   読み取りから書き込みまでを 1 つの錠で囲む。成功時は新しい指紋を返す（返さないと 2 回目が誤って拒否される）。
2. **書く前の型検査** … 新しい本文を組み立てた時点で読み直し、読めなければ書かない。
3. **書いた後の不変条件の検査** … `wbs_lint` に失敗したら元へ戻して理由を画面に出す。

**直前の操作を戻す（Ctrl+Z）**（`history.py`・`server.py` の `/undo`）：編集・追加・削除はどれも即ファイルへ書く
ので、取り消しは「その操作が触ったファイルの操作前の本文」を覚えておいて書き戻すだけにする＝逆差分もまた
1〜数行に収まり、独立レビューが成り立つ状態を壊さない。記録はプロセス内メモリだけに持つ（生成ビューに影の
状態ファイルを作らない）＝サーバが終われば消える・それより古い取り消しは git の領分。戻す前に指紋を照合し、
操作の後に別の手で正本が動いていたら**打ち切る**（推測で部分適用しない＝fail-closed）。段数は上限つき・redo は
持たない（戻しすぎたらもう一度操作する方が、redo の整合管理より安い）。

書き込みの口を開けるので、待ち受けは `127.0.0.1` だけ、合言葉は起動のたびに作って画面の本文に埋め
（URL には載せない）、独自ヘッダで送らせ、名乗ったホスト名を検査し、放っておかれたら自分で終わる。
守っているのは**ブラウザ越しの攻撃**（別のサイトからの要求・名前解決を細工した要求）で、**同じ計算機に
入れる別の利用者**は画面を読めば合言葉を取れる。共有の計算機では編集面を立てたままにしない。

バーを掴んで動かす編集は作らない。営業日への吸着と依存の玉突きを素の JS で書くと最も検査できない塊になる
（セルの編集で「参照でき編集できる」は満たせる）。

## 案件固有の上書き（`docs/wbs.yaml`）

無くてもよい。無ければ暦は土日だけを非稼働日とし、節構成は `work/` の木をそのまま使う。

```yaml
project: ○○社 需要予測基盤の構築
client: ○○株式会社
calendar:
  country: JP                       # holidays の国コード。書かなければ祝日を見ない
  extra_holidays: [2026-08-13]      # 会社・クライアントの休業日
  extra_workdays: [2026-08-22]      # 振替出勤（非稼働日の判定を打ち消す。こちらが優先）
sections:                           # 顧客向けの節。顧客の言葉と work/ の構造がずれるときの翻訳層
  - name: 要件定義
    team: コンサル
    entries:
      - work: EP-90                 # 作業単位を指す（日程・状態はそこから導出。書く欄が無い）
      - row: W-001                  # 手動行を指す
rows:                               # work/ に置けない行だけ（承認待ち・定例会議・先方の作業）
  - id: W-001
    name: 要件定義書のクライアント承認
    team: クライアント
    start: 2026-08-20
    due: 2026-08-21
    status: todo                    # 導出元が無いので必須
exclude: [EP-95]                    # 顧客向けに載せない作業単位（外すなら差分に残る形で明示する）
```

スキーマの実体は `overlay.py`。未知のキーは読み込み時に拒否される（`extra="forbid"`）ので、
導出する値（WBS 番号・日数・進捗・親の日程）を書き足すことはできない。

**手動行は節からしか置けない**（節を書かずに `rows:` だけ書くと、どこにも出ないので検査に失敗する）。
`work/` の木がそのまま顧客向けの構成でよい案件で、承認待ちを 1 行足したいだけのときは、節の `entries` に
エピックを包まず**末端の作業単位を直接並べる**と、同じ名前の階層が二重に出るのを避けられる。

**マイルストーン（◆）と定例を分ける。** ◆（`milestone: true`）は「その日に確定する出来事」（承認・検収・
成果物の期日）に予約し、ガント上部の集約行に並べて「顧客への約束の一覧」として読めるようにする。繰り返す
定例会議はマイルストーンではなく、`start`・`due` を持つ**期間のある行**（帯）として置く（`milestone` を付けない）。
こうすると新しいマーカーも種別の欄も要らず（点か期間かで既に伝わる）、`ManualRow` が「`milestone` は
`start` を持たない」を型で守るので、分離は構造的に保たれる。

## 合意した計画との差（`baseline.py`）

受託では「合意した計画」が実質的な契約の一部なので、日程が動いたときに何が・いつ・なぜ動いたかを説明
できないと信頼に直結する。ただし変更履歴の台帳を新しく作ると、書き忘れた第 1 号から嘘になる。そこで
**新しい保管場所を作らない**：

- 合意した時点＝**git のタグ**。合意したらその場で印を打つだけ（`git tag 要件定義-合意` など）。
- 変更の理由＝**その日程を動かしたコミットのメッセージ**。コミットメッセージの冒頭に作業単位の ID を書く
  ことは既に検査が強制しているので、理由は既に書かれている。書き写さない。

```
$ git tag 要件定義-合意          # 合意した時点に印を打つ
$ uv run wbs diff 要件定義-合意   # 後日、差を見る
要件定義-合意 の時点からの差（3 件）
  T-9002 実装: 予定開始 2026-08-10 → 2026-08-17　← a1b2c3d EP-90 T-9002：先方のデータ提供が遅れたため…
  T-9002 実装: 予定終了 2026-08-12 → 2026-08-21　← a1b2c3d EP-90 T-9002：先方のデータ提供が遅れたため…
  EP-90 設計フェーズ: 予定終了 2026-08-12 → 2026-08-21（配下の変更による）
```

動いていない単位は出てこない。親の行の日程は子から導いた値なので「配下の変更による」と添える
（同じ事実を 2 回主張しない）。比較のために作業ツリーは切り替えない（いまの作業を邪魔しない）。

`uv run wbs export --at <合意した時点>` で、その時点の WBS をそのまま出し直せる。刻む由来もその時点になる
（いまの HEAD ではない）ので、後から出し直しても提出したものと突き合わせられる。

## 検査（`wbs_lint.py`）

`uv run verify` が毎回走らせる。検査と表示は同じ導出を読む（画面には出るが検査は見ていない経路を作らない）。

| 止めるもの | なぜ |
| --- | --- |
| 節が指す作業単位・手動行が実在しない | 消した単位を指したままだと行が黙って減る |
| 定義した手動行をどの節も参照していない（節を書いていない場合を含む） | 書いたのに出ない |
| 節構成が `work/` の単位を覆っていない | 顧客向けから黙って消える（外すなら `exclude` に明示） |
| 2 つの節が同じ作業単位を出す（一方が親・他方がその子、も含む） | 同じ作業が 2 行になり進捗が二重に数えられる |
| 子を持つ単位が自分で `start`/`due` を宣言している | 親の日程は子から導くので、宣言した値はいつか子と食い違う |
| 先行する単位の終了予定より後続の開始予定が前 | 依存と日程の矛盾 |

## 出力形式（`formats.py`）

**既定の成果物は HTML 1 つだけ。**「同じ内容の成果物が 2 つ並んでどちらが正か分からない」状態を作らない
ため、既定で増やさない。一方で不変条件は「正本 1 つ・編集面 1 つ」であって「出力形式 1 つ」ではない
（`STATUS.md` や `docs/core.md` の自動生成節と同じ形＝1 つの正本から複数のビューを出すのは元からの作法）。

先方の様式指定がある案件のために、**その依存が入っている案件でだけ形式が生える**（モデルの保存形式・
モデル種と同じ条件登録）。入れなければ一覧にも出ないので、選べる形式＝使える形式になる。

| 形式 | 要る依存 | 中身 |
| --- | --- | --- |
| `html` | （既定・追加なし） | 自己完結 HTML 1 ファイル |
| `xlsx` | `uv sync --extra deliver --extra openpyxl` | 表計算の写し（`xlsx.py`。階層は折りたたみ、週ごとの塗りでガント） |

```
uv run wbs export --format xlsx --out 提出用.xlsx
```

表計算の写しは**読み取り専用**。シートの先頭に「正本は work/。この表への記入は取り込まれません」と書く。
**取り込みは作らない**：表計算は編集を誘う道具なので、返送されたファイルを読む口を開けると、行の挿入・
並べ替え・書式でセルの対応が黙って壊れる（＝二重台帳への入口）。クライアントの変更の要望は要求層
`docs/demands/` で受ける。

形式を足すときは、`write(wbs, path, *, provenance, draft)` の形の関数と拡張子を `formats.py` に登録するだけ
でよい（導出は 1 か所にあるので、形式側は書き出すだけ。拡張子も登録簿が持つので別の対応表は要らない）。

描画の作りは `render.py`。左に表・右に大きな 1 枚のガント、という 2 枚組にはせず、1 つの表にして
バーを各行のセルの中に描く（改ページで行とバーがずれない・時間軸の見出しが各ページに再掲される）。
各行には**共通の下敷き**（時間軸の格子・今日の線）を敷く＝棒だけだと時間の目盛が無く、
棒の長さが何日なのか読めない（図表に見えない）。格子は軸の目盛と同じ位置なので、上の見出しと目で繋がる。
格子は線種で 3 段（日／週／月）に固定し、**どのズームでも「選んだ単位＋1 つ細かい単位」を常に出す**（月表示でも
週線が入り、棒の無い空白も方眼に見える）。マイルストーンの集約行にも同じ下敷きを敷く（◆の日付が方眼で読める）。
描画の期間はデータの期間を**月の境目まで広げる**（1 日始まり・月末終わり）。日を数字で並べたときに
「1 から月末まで」になり、何月の何日を見ているのかが読める。月の見出しの区切りとも位置が合い、数日しか
ない案件で棒が列の端から端まで伸びて「ただの帯」になる問題も同時に解ける（1 か月は必ず 28 日以上ある）。
横軸は暦日、日数の列は営業日。時間軸の目盛は期間の長さで間引く（数年の案件で日付が重なって読めなくなる
のを防ぐ）。日程が片端しか無い行（開始だけ・終了だけ）は棒を描けないので「未日程」の印を付ける
（ガントの列が無言の空白にならない）。CLI の入口は `cli.py`。
