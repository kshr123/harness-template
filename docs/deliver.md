# deliver — クライアントに見せる WBS とスケジュール（ガント）

- **読者**：人（案件の計画を顧客と合意し、進捗を報告するコンサル／その提出物の由来を確かめたい人）
- **種別**：reference（使い方と提出の作法）
- **分かること**：WBS・ガントを何から・どう出すか、何を書けば計画が正しく射影されるか
- **ここからやること**：`uv sync --extra deliver` → `uv run wbs export` で提出物を出す。設計の内部は `docs/deliver-code.md`

案件の計画をクライアントと合意し、定例会議で進捗を報告し、最終報告で計画と実績を並べるための
WBS（Work Breakdown Structure＝作業を分解した一覧）とガント（工程を横棒で表した図）を出すプロファイル。

- **実装**：`src/harness/deliver/`（各ファイルの役割・描画/編集の設計は `docs/deliver-code.md`）
- **場面ごとの手順**（提案・定例・引き直し・最終報告）：`.claude/skills/wbs/SKILL.md`
- **案件を始めるときの上書きの雛形**：`.harness/templates/wbs.yaml`

## 考え方（これだけは先に読む）

**WBS はデータではなくビュー。日程の正本は `work/` の作業単位の木ひとつ。**
WBS 専用のファイルに階層と日程を持たせると同じ事実を 2 回書くことになり、必ずどちらかが古くなる。だから
このプロファイルは木を顧客向けに射影するだけで、日程を保存しない。

| 情報 | どこにあるか |
| --- | --- |
| 階層 | `work/` のフォルダ構造（親はフォルダ） |
| 予定開始・予定終了・見積り工数・マイルストーン | 作業単位の frontmatter（`start`・`due`・`effort_days`・`milestone`） |
| 状態 | 作業単位の `status`（下の表） |
| 実績開始・実績終了 | 作業単位の `created`・`closed` から導出（未着手の行には出さない） |
| WBS 番号・営業日数・進捗・親の日程 | **どこにも無い**（毎回導出する。書く欄が存在しない） |
| 担当・チーム | 作業単位の `owner`・`team`（名簿は `docs/wbs.yaml` の `members`・`teams`） |
| 暦・顧客向けの節構成・手動行・名簿 | `docs/wbs.yaml`（案件固有の上書き。数十行） |

**状態の意味**（進み具合の目盛ではなく、**誰の手番か**で分かれる）：

| 表示 | 値 | 意味 | 機械の扱い |
| --- | --- | --- | --- |
| 未着手 | `todo` | まだ始めていない | 依存が全部 done なら着手候補に出る |
| 進行中 | `in-progress` | **いま手が動いている** | `uv run status --next` の先頭（再開の候補） |
| 確認待ち | `in-review` | **作る側の手は離れ、確認する人の判断を待っている** | 「人の判断待ち」に集まる |
| 保留 | `blocked` | 進められない（障害・外部待ち） | 「人の判断待ち」に集まる／親を畳むとき最も強い |
| 完了 | `done` | 検証に成功した | **自己申告では置けない**（`verified_by` が要る） |

- 見分け方：**進行中↔確認待ち**は手が動いているか／人の判断を待っているか。**確認待ち↔保留**は待つものが
  「確認」か障害か。**未着手↔保留**は着手していないだけか／着手できないか。
- **確認待ちと保留だけが「人を呼ぶ状態」**で、`uv run status` に集約される。
- 1 行の意味は成果物自身が持つ（状態のセルにかざすと出る）＝docs を読まないと分からない状態を作らない。
- **親の行の状態は子から畳む**：全部 done なら完了／1 つでも保留なら保留（最悪が勝つ）／1 つでも動いていれば
  進行中／それ以外は未着手。親は自分の状態を持たない（持たせると子と食い違う）。導出の規則は `docs/deliver-code.md`。

## 使い方（How-to）

```
uv sync --extra deliver
uv run wbs edit [--port <番号>] [--today YYYY-MM-DD] [--idle-minutes 60] [--root <プロジェクトの根>]
uv run wbs export [--out <出力先>] [--format html] [--today YYYY-MM-DD] [--at <合意した時点>] [--against <合意した時点>] [--draft]
uv run wbs report [--against <合意した時点>] [--out <出力先>] [--today YYYY-MM-DD] [--horizon-days 14] [--draft]
uv run wbs diff <合意した時点> [--today YYYY-MM-DD] [--root <プロジェクトの根>]
uv run wbs formats
uv run wbs lint [--today YYYY-MM-DD]
```

- `uv run wbs edit` … 手元のブラウザで見ながら直す。表示された `http://127.0.0.1:<番号>/` を開き、セルを
  クリックして編集（Enter で保存・Esc で取り消し）。編集の仕組みと安全策は `docs/deliver-code.md`。
- `uv run wbs export` … 自己完結の HTML を 1 ファイル出す（既定 `artifacts/wbs/WBS.html`）。外部リソースを
  読まないのでそのままクライアントへ送れる。ブラウザの印刷から PDF にできる（A3 横）。`--against <合意した
  時点>` を付けると、その時点の棒を淡色で現状の棒に重ねる（計画対比＝ベースライン。HTML だけ・`--at` とは排他）。
- `uv run wbs report` … 定例・最終報告の **1 枚**（自己完結 HTML）。マイルストーンの状況・遅れている作業・
  今後 N 日の予定をまとめ、**要件トレース**（要件→作業→状態・未カバーの要件）を付録に出す（要件文書が無い
  案件では出さない）。`--against` で前回からの計画の変化も先頭に出す。拒否条件は export と同じ関門を通る。
- `uv run wbs diff <合意した時点>` … 合意した計画といまの計画の差を並べる（下の「合意した計画との差」）。
- `uv run wbs formats` … 出せる形式の一覧（入れていない依存の形式はここに出ない）。
- `uv run wbs lint` … `uv run verify` が回すのと同じ WBS の検査だけを単体で走らせる。

**出力を拒否する場合**（既定を不合格側に置く）：

- 検査に失敗する状態のとき（間違った工程表を良い見た目で渡さない）。
- 日程を持つ作業単位が 1 件も無いとき（空の工程表を黙って渡さない）。
- **WBS の入力**（`work/` と `docs/wbs.yaml`）に未コミットの変更があるとき（生成物に刻むコミットが実際の
  中身と食い違う＝由来が嘘になる）。定例の直前に 1 行直してすぐ出す実務のために `--draft` を残してあるが、
  そのときは生成物に「下書き」と出る。

## 提出物の体裁と由来

顧客に渡す 1 枚がどう見えるか（描画の内部＝`_STYLE`・貼り付く列・重ね順などは `docs/deliver-code.md`）。

- **色は 3 色＋警告の 1 色**（白・黒・青＋赤）。**赤は「遅れ」だけ**・**ガントの棒は 1 色（青）**で、状態は
  行の側で示す（棒と行で二重に持たない）。明暗どちらの地でも読め、白黒で刷っても状態の強さの順が保たれる。
- **折りたたみ** … 親の行の取っ手で畳める（見出しに「全部閉じる／全部展開」）。畳んだ行も印刷では必ず戻す
  （白紙のフェーズを渡す事故が起こらない形）。
- **時間軸** … 見出しの「月／週／日」で切り替える。粒度ごとに幅が変わり、棒も格子も同じ表の中で伸び縮みする
  （行と棒がずれない）。紙では必ず全期間を収める。
- **完了した行は落ち着かせる**（取り消し線は付けない＝実績の日付は読ませる。棒だけ淡くして地に沈める）。
- **非稼働日**（土日・祝日・案件の休業日）は淡い面で沈める（どの列が休みか数えずに読める）。
- **作業単位の ID**（`EP-`・`T-`・`W-`）は閲覧では出さない（クライアントに関係ない）。「未日程」の一覧も
  出さない（日程の無い行はガントが空なので見れば分かる）。
- **由来の刻印**（`stamp.py`）… 見出しに「コミット・生成日時・内容の指紋」を出す。指紋は表に出ている値
  そのものから作るので、コミットが同じでも中身が違う／コミットが違っても中身は同じ、を見分けられる。
- **作業名**は frontmatter の `title`、無ければ本文の見出し（`# <ID> タイトル`）から ID を除いて拾う
  （title を書かない案件でも名前が ID にならない）。

## 案件固有の上書き（`docs/wbs.yaml`）

無くてもよい。無ければ暦は土日だけを非稼働日とし、節構成は `work/` の木をそのまま使う。

```yaml
project: ○○社 需要予測基盤の構築
client: ○○株式会社
calendar:
  country: JP                       # holidays の国コード。書かなければ祝日を見ない
  extra_holidays: [2026-08-13]      # 会社・クライアントの休業日
  extra_workdays: [2026-08-22]      # 振替出勤（非稼働日の判定を打ち消す。こちらが優先）
sections:                           # 顧客向けの節。顧客の言葉と work/ の構造がずれるときの翻訳層
  - name: 要件定義
    team: コンサル
    entries:
      - work: EP-90                 # 作業単位を指す（日程・状態はそこから導出。書く欄が無い）
      - row: W-001                  # 手動行を指す
rows:                               # work/ に置けない行だけ（承認待ち・先方の作業。定例会議は events へ）
  - id: W-001
    name: 要件定義書のクライアント承認
    team: クライアント
    start: 2026-08-20
    due: 2026-08-21
    status: todo                    # 導出元が無いので必須
exclude: [EP-95]                    # 顧客向けに載せない作業単位（外すなら差分に残る形で明示する）
```

スキーマの実体は `overlay.py`。未知のキーは読み込み時に拒否される（`extra="forbid"`）ので、導出する値
（WBS 番号・日数・進捗・親の日程）を書き足すことはできない。

- **手動行は節からしか置けない**（節を書かずに `rows:` だけ書くと、どこにも出ないので検査に失敗する）。
- `work/` の木がそのまま顧客向けの構成でよい案件で承認待ちを 1 行足すだけなら、節の `entries` にエピックを
  包まず**末端の作業単位を直接並べる**と、同じ名前の階層が二重に出るのを避けられる。

## マイルストーンか出来事か

**「完了条件があるか」だけで決める**（会議かどうかでは決めない）。次の 2 つを問う：**「終わったか」を追う
対象か／他の作業がそれを待つか**。どちらも「はい」ならマイルストーン、どちらも「いいえ」なら出来事。

| | 「終わったか」を追う | 依存される | 置き場 |
| --- | --- | --- | --- |
| 定例会議（隔週） | いいえ（第 3 回の「完了」に意味が無い） | いいえ | `events`（出来事） |
| 最終報告会 | **はい**（実施して報告書を出したか） | **はい**（検収が待つ） | `work/` の `milestone: true` |
| 承認・検収・要件確定 | はい | はい | `work/` の `milestone: true` |

- **会議かどうかは関係ない**。毎週の定例も最終報告会も会議だが、前者に完了は無く後者にはある。型がこれを
  教える：`Event` には `status` の欄が無いので、**「完了を記録したい」と思った時点で、それは出来事ではない**。
- **マイルストーン（◆）** … `milestone: true`。ガント上部の集約行に並べ「顧客への約束の一覧」として読める。
  画面から登録すると `work/` 直下に作業単位を作る（完了を追う対象なので木に載る）。
- **出来事（`events`）** … 「完了状態を持たない、有限個の開催日の集合」。隔週の定例に長い帯を引くと「ずっと
  やっている」という嘘になるので、**期間でなく開催日の集合**として持つ。語彙は RFC 5545（`dtstart`／`rrule`／
  `rdate`／`exdate`）をそのまま使い、`rrule` には UNTIL か COUNT が必須（開催日が有限であることを合格条件に
  含める）。画面からは繰り返しを操作で入れるだけで登録でき、RRULE の文字列は出さない（内部設計は
  `docs/deliver-code.md`）。ガント上部のレーンで種類（マイルストーン／定例／社内）を分ける。

## 合意した計画との差（`baseline.py`）

受託では「合意した計画」が実質的な契約の一部なので、日程が動いたときに何が・いつ・なぜ動いたかを説明
できないと信頼に直結する。ただし変更履歴の台帳を新しく作ると書き忘れた第 1 号から嘘になる。そこで
**新しい保管場所を作らない**：

- 合意した時点＝**git のタグ**（合意したらその場で印を打つ。`git tag 要件定義-合意` など）。
- 変更の理由＝**その日程を動かしたコミットのメッセージ**（冒頭に作業単位 ID を書くことは既に検査が強制して
  いるので、理由は既に書かれている＝書き写さない）。

```
$ git tag 要件定義-合意          # 合意した時点に印を打つ
$ uv run wbs diff 要件定義-合意   # 後日、差を見る
要件定義-合意 の時点からの差（3 件）
  T-9002 実装: 予定開始 2026-08-10 → 2026-08-17　← a1b2c3d EP-90 T-9002：先方のデータ提供が遅れたため…
  T-9002 実装: 予定終了 2026-08-12 → 2026-08-21　← a1b2c3d EP-90 T-9002：先方のデータ提供が遅れたため…
  EP-90 設計フェーズ: 予定終了 2026-08-12 → 2026-08-21（配下の変更による）
```

動いていない単位は出てこない。親の行の日程は子から導いた値なので「配下の変更による」と添える（同じ事実を
2 回主張しない）。`uv run wbs export --at <合意した時点>` で、その時点の WBS をそのまま出し直せる（刻む由来も
その時点になるので、後から出し直しても提出したものと突き合わせられる）。

## 検査（`wbs_lint.py`）

`uv run verify` が毎回走らせる。検査と表示は同じ導出を読む（画面には出るが検査は見ていない経路を作らない）。

| 止めるもの | なぜ |
| --- | --- |
| 節が指す作業単位・手動行が実在しない | 消した単位を指したままだと行が黙って減る |
| 定義した手動行をどの節も参照していない（節を書いていない場合を含む） | 書いたのに出ない |
| 節構成が `work/` の単位を覆っていない | 顧客向けから黙って消える（外すなら `exclude` に明示） |
| 2 つの節が同じ作業単位を出す（一方が親・他方がその子、も含む） | 同じ作業が 2 行になり進捗が二重に数えられる |
| 子を持つ単位が自分で `start`/`due` を宣言している | 親の日程は子から導くので、宣言した値はいつか子と食い違う |
| 先行する単位の終了予定より後続の開始予定が前 | 依存と日程の矛盾 |

## 出力形式（`formats.py`）

**既定の成果物は HTML 1 つだけ。**「同じ内容の成果物が 2 つ並んでどちらが正か分からない」状態を作らない
ため既定で増やさない。先方の様式指定がある案件のために、**その依存が入っている案件でだけ形式が生える**
（入れなければ一覧にも出ない＝選べる形式＝使える形式）。

| 形式 | 要る依存 | 中身 |
| --- | --- | --- |
| `html` | （既定・追加なし） | 自己完結 HTML 1 ファイル |
| `xlsx` | `uv sync --extra deliver --extra openpyxl` | 表計算の写し（`xlsx.py`。階層は折りたたみ、週ごとの塗りでガント） |

```
uv run wbs export --format xlsx --out 提出用.xlsx
```

表計算の写しは**読み取り専用**（先頭に「正本は work/。この表への記入は取り込まれません」と書く）。**取り込みは
作らない**：返送ファイルを読む口を開けると行の挿入・並べ替え・書式でセルの対応が黙って壊れる（二重台帳への
入口）。クライアントの変更の要望は要求層 `docs/demands/` で受ける。形式を足す手順は `docs/deliver-code.md`。
