# 開発の進め方と、それ自体が進化する仕組み

この文書は、この基盤であらゆる開発・運用をどう進め、どう良くしていくかを定めた、唯一の正とする文書（正本）
（メタ設計＝進め方そのものの設計）。役割分担として、強制ルールは `AGENTS.md`、
実行時の手引きはスキル、変更の経緯は git（コミット）が持ち、この文書は「なぜ・全体像・ルール化の流れ」だけを持つ
（同じ文を他所に重複させない＝F 節）。進め方を変えたい・新しいルールを足したいときに読む。

## A. 標準の進め方（既定）：全体→詳細

**既定の手順**：どんな新機能・新案件でも、次の順で進める。
1. **端まで通る最小の骨組みを先に作る**（入力→処理→出力→検証が一巡する最小の実装。中身は仮でよいが `uv run verify` は通す）。
2. **検証が全成功の状態を保ったまま**、骨組みの各部を本実装で差し替える。差し替えの順番は自由（リスクが高い所・分からない所から）。
3. 差し替えのたびに独立レビュー→verify 全成功→コミット。

**なぜ既定か**：
- 結合の失敗（部品は動くが繋がらない）を最初に潰せる。AI コーディングは部品生成が速い反面、結合の誤りが残りやすく、先に一巡を通すのが最も効く。
- 常に「動く全体」があるので、どの時点で中断しても価値が残り、独立レビューが差分だけで判断できる。
- 「計画は近い作業だけ詳しく」（AGENTS 原則）とかみ合う。骨組み＝全体の outline、差し替え＝detailed、と計画の粒度がそのまま実装の粒度になる。

**いつ例外か**：
- 1 ファイルで完結する修正・障害対応（骨組みを作る意味がない・直接直して verify）。
- kind が調査（成果物は結論節で骨組みが無い）。
- 既に骨組みが通っている領域への追加（その上で差し替えを続けるだけ）。

**既存スキルとの関係**：session＝読み始めと終わり方、implement＝1 つの変更の作法、plan＝分解。この「最小の骨組みを先に作る」進め方は「エピックを分解するときの順序の決め方」なので plan の手順と AGENTS の原則に 1 行ずつ据える（新スキルは作らない）。

## B. 「進め方」の階層モデル

働き方は 6 つの層でできている。下の層ほど強制力が強い。

| 層 | 何か | どこに住むか | 機械で担保できるか | 例 |
|---|---|---|---|---|
| 機械検査 | 違反すると verify が失敗する検査 | `harness/`（pm.lint・spec_lint・checks.toml）＋ pytest/ruff/mypy | **完全** | done↔verified_by の実在検査 |
| 抽象（拡張ポイント） | 変わりうる部分を切り離す型・設定 | Protocol 定義（満たすべきメソッドだけ定めた差し替え用の型）・config の backend URI（保存先などを差し替える裏側の指定）・レジストリ（名前で部品を引ける登録簿） | **ほぼ完全**（mypy が担保） | 保存形式は manifest（保存物に付く由来書き）の `format` 文字列で分岐（核が形式ライブラリを固定しない） |
| 規約 | 人と AI が従う決まりごと | `AGENTS.md`（正本） | **部分的**（各項目が検査点を括弧書き。持てない項目は「レビュー観点」） | 「テストの数値は構成由来」 |
| スキル | セッション中に実行する手順の手引き | `.claude/skills/*/SKILL.md` | 不可（発火は description の語） | harvest：振り返り→learnings 記録 |
| 気づき | まだルール化していない観察の材料 | `docs/learnings.md` | 不可（見直しで管理） | L-004 生成物のコミット強制は摩擦 |
| 記憶（Claude memory） | 案件・リポをまたぐアシスタント個人の作法 | Claude 側の memory | 不可 | 「造語を使わない」 |

**層をまたぐ一貫性（3 規則）**：
1. **1 つの文の正本は 1 か所**。他の層はリンクで参照する（例：AGENTS の 1 行ルールに理由の一節を添え、深い経緯は git）。
2. **参照は下向きのみ**：気づき→（規約・検査・抽象・スキル）。検査コードが learnings を参照する逆向きは作らない。
3. **記憶（Claude memory）はリポの正本にしない**。リポに影響する事実・ルールは必ず learnings か AGENTS に落とす。memory は「私（アシスタント）がどう振る舞うか」だけ。リポは memory 無しでも完結する（別のエージェント・人が来ても働ける）。

## C. 進化の仕組み（気づきを資産にルール化し、後戻りさせない）

ここでのルール化＝作業中の気づきを、ルール・部品に「格上げ」すること。

**ルール化の流れ（正本の手順）**：
```
観察（作業中に困った・工夫した）
  → learnings に 1 項目（状態: 記録のみ）        …コストほぼゼロ、必ず書く
  → 価値/一般性があると判断したら即、落とし先を 1 つ選ぶ（回数は待たない）
  → 落とし先に実装し、learnings を（状態: ルール化済み）に更新
  → 次の見直しでルール化済み項目を削除（正本が移ったので）
```

**落とし先の判定表**（上から順に検討）：

| 気づきの性質 | 落とし先 |
|---|---|
| 合否を機械で判定できる | 機械検査（pm.lint / spec_lint / checks.toml / pytest） |
| 「変わりうる軸」の発見 | 抽象（Protocol・config URI） |
| セッション中の手順（3 手以上） | スキル |
| 上のどれでもないが従うべき | AGENTS に 1 行＋「レビュー観点」の印 |

**ルール化の基準**：**必要になった時に即ルール化**（回数で待たない）。
- 歯止めは「回数」でなく「一般性」の判断＝一般的・再発する形が見えているものをルール化し、**その 1 回限りと分かっている工夫はルール化しない**（learnings 止まり）。判断軸は「作るか sklearn で足りるか」や「差し替え軸が既知か」と同じ。
- **後戻り防止は据え置き**：即ルール化でも「違反すると失敗する検査」を先に書いてから直す（下段）。
- 事故防止（データ破壊・秘密情報）と差し替え軸が既知のもの（保存形式・モデル・保存先の Protocol / URI）は元から即時＝この既定に合流する。

**降格・削除**：learnings はルール化済み・古い項目を見直しで消す（既定は harvest 実行時）。スキルは使われなくなったら統廃合し、大きな廃止はコミットに理由を 1 行残す（版番号は付けない・git が履歴）。機械検査の撤去は理由をコミットに残す（L-004 の status 一致ゲート撤去が先例）。

**後戻りの防止（機械的な裏付け＝一度上げた基準を戻さない歯止め）**：ルールを機械検査に落とすときは**先に「違反すると失敗する検査」を書いてから直す**（テスト先行と同じ）。検査がある限り、将来のセッションが知らずに退行しても verify が止める。検査にできないルールだけが「レビュー観点」に残り、review スキルの確認項目になる。

## D. ルール化の原則

**durable なルールは、可能な限り機械的な強制点を持つ。レビューは強制点を持てないものの受け皿であり、既定ではない。**

**新ルールの足し方**：
1. 根拠を書く（軽微なら learnings、大きな方針転換はコミットメッセージに理由）。
2. 強制点を選ぶ：作業単位の構造→pm.lint／文書の形→spec_lint／コードの振る舞い→pytest・checks.toml／書き方→ruff／型→mypy。
3. 検査を先に足し、既存の違反を直し、verify を全成功に戻す。
4. AGENTS に 1 行足し、末尾に強制点を括弧書きする（例：「グローバルな種設定は禁止（spec_lint が `np.random.seed` を検出）」）。
5. 強制点を持てないルールは AGENTS 内で「（レビュー観点）」と明記する。review スキルはその印の付いた項目を確認する。

これにより AGENTS.md 自体が「どのルールが機械で守られ、どれが人（レビュー）頼みか」の一覧になる。**括弧書きの無いルールを増やさないこと**が規約の腐敗を防ぐ歯止め。

## E. スキル化の設計

**スキルにするもの**：セッション中に繰り返し実行する・3 手以上の手順で・間違えると高くつくもの。この 3 条件を満たさなければスキルにしない（AGENTS の 1 行か learnings で足りる）。
**形（現行維持）**：frontmatter（name・発火語入りの description）＋手順（番号付き）＋してはいけないこと。1 スキル 20 行前後・超えたら分割でなく削る。
**進化**：修正は普通のコミット。統廃合・廃止はコミットに理由を 1 行（版番号は付けない）。
**過剰化を避ける**：スキル追加もルール化の一種で C 節の基準に従う（回数でなく「繰り返す手順だと見えたら即」作る）。歯止めは E 節冒頭の 3 条件（3 手以上・繰り返す・間違えると高い）を満たすか＝*generality* の判断で、1 回限りの手順はスキルにしない。

**部品と、それを使える状態にする作業は 1 タスク**：部品を作る工程と「エージェントがそれを見つけて使えるようにする」工程を分けると、使えるようにする作業だけが永遠に積み残る（EP-06 の実例：BLOCKS/ENCODERS はあるが一覧も experiment スキルも無く、雛形が部品を使っていなかった）。正本は機械可読カタログ（レジストリ）で、一覧コマンド（`uv run data blocks` / `data encoders`）はそこから生成し、スキルは一覧へ導くだけにする（一覧を手書きしない＝二重管理を作らない）。部品の完了条件は DoD／AGENTS の「部品は、他の人が元コードを読まずに使える状態にして完了」。

**ML フェーズのスキルは最小 2 つ**（新しい作業種別を始めるための例外）：`experiment`（実験の回し方＝雛形をコピーし config だけ書く）と `features`（特徴量の足し方＝部品カタログへ辿り着けるようにする案内＋作る/使うの判断）。`eda` は最初の調査 kind の実験と同じタスクで作る（部品と、それを使えるようにする作業は 1 タスク）。

参考リポの feature/training/tuning/ensemble/evaluation は**取り込まない**（我々は「実験＝1 仮説＋設定の変種」なので experiment の 1 手順に畳める。スキルを増やすと発火が割れる）。checklist は session と重複、testing は AGENTS のテストの決まりごとが正本なので不採用。

## F. 成果物の置き場と一貫性

このメタ設計の置き場：`docs/method.md`（本文書＝正本）＋ AGENTS.md への 1 行追記（既定の進め方）。**AGENTS に全文を取り込まない**（AGENTS は短い決まりの場所・思想を混ぜると読み込みすぎを招く）。

| 場所 | 書くこと | 書かないこと |
|---|---|---|
| AGENTS.md | 従うべき決まり（1 行＋強制点の括弧書き） | 理由・経緯・手順の詳細 |
| docs/method.md | なぜ・全体像・ルール化の流れ | 個別ルール本文（AGENTS へ）・手順の実行形（スキルへ） |
| .claude/skills | セッション中の手順の実行形 | 理由（method へ）・ルール本文（AGENTS へ） |
| docs/learnings.md | 未ルール化の観察 | ルール化済みの内容（消す） |

## G. この基盤の自己適用

基盤自身が最初の案件（charter の思想）。この手順は、まずこの基盤の開発に適用する。
**EP-06（DS 実験ループ）での実例**：
- 最小の骨組み＝「データ読み込み→fold（交差検証でデータを分けた 1 区画）→特徴→学習→評価→results 記録」が `--test` で一巡し verify が通る最小実装（E-0001 の baseline・DESIGN.md E）。以降のタスク（特徴の本実装・閾値・台帳）は緑を保ったままの差し替えとして積む。
- 差し替え軸は sklearn Pipeline を背骨に、特徴量は `BLOCKS`・エンコーダは `ENCODERS`・モデル種は `MODELS`・保存形式は manifest の `format` 文字列で持つ（当初案の自前 Protocol 層は過剰分割だったため撤回）。

**今すぐ入れた最小**：本文書（method.md）／AGENTS 原則に「着手は全体→詳細」1 行／plan スキルの分解手順に「最初のタスクは端まで通る最小の骨組み」1 行／harvest を C 節の 5 手順へ／learnings 書式に「状態」欄（L-004 をルール化済みに）。
**後で足す分（通常タスク）**：spec_lint に `np.random.seed` 検出（AGENTS 既存ルールへ強制点を付ける最初のケース）／`experiment`・`eda` スキル（EP-06 着手時）。

## H. 既定＋上書き条件（業務価値の点のみ）

1. **着手順は骨組み優先が既定**。上書き：障害対応・期日が迫った一点修正は直接直してよい（verify 全成功は譲らない）。
2. **ルール化は「必要になった時に即」が既定**。歯止め（回数でなく一般性の判断）の正本は C 節＝ここでは繰り返さない。上書き：データ破壊・秘密情報の漏えいを防ぐ検査は指摘の時点で即（事故のコストが常に上回る）。
3. **スキル追加も「繰り返す手順だと見えたら即」が既定**。歯止めは E 節の 3 条件（3 手以上・繰り返す・間違えると高い）。新しい作業種別を始めるときは最小のフェーズスキルを先に用意してよい。
