# learnings（気づき・使いにくかった点の記録）

この文書は、作業で得た気づき・使いにくかった点を、ルールへ格上げ（ルール化）する前の
材料として記録する場所。同じ失敗を繰り返さないために、作業者（ユーザー・エージェント）が随時書く。
1 件＝1 項目で、冒頭に要点、続けて背景と対応。リポジトリや履歴が既に記録することは書かない。古くなったら消す。

各項目は「状態」を持つ：
- **記録のみ** … まだルール化していない観察。
- **ルール化済み** … 機械検査・抽象・スキル・規約のどれかへ落とした（現在のルールは AGENTS/method/検査が正本。経緯は git）。次の見直しで消す（ただし他の learnings の**根拠として引用されている**ものは、引用先が迷子にならないよう先例として保持する＝L-004 の扱い）。

ルール化の流れは `docs/method.md` C 節、実行手順は harvest スキル。L-001〜003・005〜006 は実装知識でルール化不要（記録のみ）。L-004 はルール化済み（生成物 STATUS の扱い）で、後戻り防止（歯止め）の先例。

---

## L-001 Windows のコンソール（cp932）は ✓ などの記号を出せず落ちる
- **要点**：出力に `✓✗` や日本語があると、Windows の既定の文字コード（cp932）で `UnicodeEncodeError` になり落ちる。
- **対応**：CLI の起点（`harness/cli.py`）で `sys.stdout/stderr.reconfigure(encoding="utf-8")` を最初に実行し、出力を UTF-8 に固定。「make に依存しない＝複数の OS で動く」前提の一部。
- **設計への反映**：不要（実装で解決）。「CLI は UTF-8 に固定する」は AGENTS.md の範囲で足りる。

## L-002 mypy strict ＋ 型情報の無い外部ライブラリ（python-frontmatter）は取り込みで失敗する
- **要点**：strict だと、型情報の無いライブラリの取り込みで失敗する。
- **対応**：`pyproject.toml` に `[[tool.mypy.overrides]] module=["frontmatter"] ignore_missing_imports=true` を追加。
- **設計への反映**：不要。新しい外部ライブラリを足したとき同じ設定が要ることがある、と覚えておく。

## L-003 日本語のコメント・メッセージは ruff の行の長さにすぐ当たる
- **要点**：日本語は文字が詰まるため、説明的な文が長くなりやすい。造語を使わず平易に書くと、なおさら長くなる。
- **対応**：行の長さを 120 に上げた（`pyproject.toml` の `[tool.ruff] line-length = 120`）。平易な日本語の説明を優先するための判断。
- **判断**：当初は 100（標準）にしていたが、平易な言葉を優先する方針で頻発したため 120 に変更した。

## L-004 生成物（STATUS.md）をコミットしてソースと一致を強制すると、作り直し忘れで検証が落ちる
- **状態**：ルール化済み（機械検査＝一致ゲートの撤去へ落とした。次の見直しで削除してよい・method.md の先例として当面残す）。
- **要点**：STATUS.md をコミットし、`work/` と一致するかをコミット前の検査・CI で突き合わせていた。`work/` を変えた後に `uv run status` を忘れると検証が落ちる摩擦が繰り返し起きた。「人が張り付かず仕組みで品質を担保する」狙いに反するノイズだった。
- **対応**：生成物なのでコミットしない方針に変えた（`.gitignore`・追跡から外す）。一致ゲート（コミット前フック・CI の `status --check`・`checks.py` の一致確認）を撤去。見たいときに `uv run status` で作り直す。
- **判断**：生成物を版管理してソースと同期させる仕掛けは「生成し忘れで落ちる」失敗を生むだけで正しさに寄与しない。ソースは常に `work/` の木であり、一覧はそこから機械的に導ける。撤去して摩擦を根本からなくした。

## L-005 Windows で git が改行を CRLF に変換する警告を出す（複数 OS で差分の原因になる）
- **要点**：Windows の作業コピーで改行が CRLF になり、Linux の CI と差分になりうる。
- **対応**：`.gitattributes` に `* text=auto eol=lf` を置き、改行を LF に統一。
- **設計への反映**：不要（テンプレートの標準装備として `.gitattributes` を含める）。

## L-007 業界標準（scikit-learn）があるのに評価メトリクス・標準化・CV 分割を自前で書いていた
- **状態**：ルール化済み（「標準ライブラリを再発明しない」を AGENTS のレビュー観点に落とした。先例として当面残す）。
- **要点**：roc_auc・accuracy・StandardScale・fold 分割を numpy で手書きしていた。これは業界標準の再発明で、保守負債・バグの温床だった（参考リポも全メトリクスを sklearn 実装）。

## L-006 typer.Exit を console_script の起点で raise すると余計なエラー表示が出る
- **要点**：`[project.scripts]` の起点となる関数（typer.run を通さない）で `raise typer.Exit(1)` すると、捕捉されず余計なエラー表示（Traceback）が出る（終了コードは 1 で正しいが見苦しい）。
- **対応**：起点では `sys.exit(1)` を使う（task-lint・status・verify）。typer.run を通すコマンド（check）は typer.Exit のままでよい。
- **設計への反映**：不要（実装の作法）。自分たちで使って試す中で見つかった＝仕組みが働いている例。

## L-009 合否の判定を `<`/`>` の対で書くと NaN が両方 False で通過する（fail-open）
- **状態**：ルール化済み（`harness.gates` が判定の唯一の実体。`value_threshold` / `change_threshold` の両方で有限性を合格条件に含める）。
- **要点**：`if value < limit: return False` / `elif value > limit: return False` の形は、`value` が NaN のとき両方の比較が False になり、合格側へ**開いて**通ってしまう。発散モデルの `log_loss=nan`/`rmse=nan` が `value_threshold` を通り champion への採用まで届きうる（ds レビュー 2026-07-05）。
- **対応**：**合格条件を正の形で 1 度だけ書き、満たさなければ落とす**：`ok = value >= limit if higher_is_better else value <= limit; if not ok: return False`。NaN は「満たさない」に倒れて閉じる。
- **続き（T-0176）**：正の形だけでは足りない。**比較が行われない経路と、比較を満たしてしまう発散値**が残る。(a) `inf >= limit` は True なので上限・下限の比較では止まらない。(b) 比較対象の無い初回昇格では比較そのものが実行されず、閾値が 1 つも宣言されていなければ判定が 1 件も課されない。実際 NaN の版が champion になり、以後どの候補も改善量が NaN で永久に昇格できない状態を作れた。合格条件に `math.isfinite(value)` を含めて初めて「発散した版は昇格しない」と言える。
- **判断**：止める検査・合否・フィルタは既定を「不合格側」に置く（fail-closed）。**「NaN でない」ではなく「有限である」を条件に書く**（発散は NaN だけで起きない）。そして「この経路では判定が 1 件も走らない」場合を数える（0 件の判定は常に合格する）。

## L-010 手書きのデータ検証は、ライブラリが吸収するエッジケースを落とす
- **状態**：記録のみ（「標準を再発明しない」の 2 回目の実例。手書き検証を続けるか pandera へ導出するかは未決）。
- **要点**：`schema.validate` を手書きしていたため、parametrized dtype（`Datetime(...)`≠`"Datetime"`）・NaN が null 検査をすり抜ける・複合キー未検査・null 数で一意判定がぶれる、の 4 つを同時に落としていた（ds レビュー 2026-07-05）。これらは `pandera.polars` が既に正しく扱う領域。
- **対応**：今回は 4 穴を手書きのまま塞いだ（テスト付き）。ただし cross-column の `checks` 評価まで手で作り込むより、正本 YAML から pandera 実行器を導出する方が筋（採否は未決）。
- **判断**：L-007（メトリクス・CV 分割の手書き）に続く「標準の再発明」の 2 例目。検証器も『核は形式ライブラリを直接固定しない・実行器は正本からの導出物』の考え方を検証に広げるかを次に決める。

## L-013 案内の書き忘れ（missing link）は一方向の doclint では捕まらない
- **状態**：ルール化済み（案内カバレッジ検査 coverage_lint を verify に接続。先例として当面残す）。
- **要点**：doclint は「書いた参照が実在するか」（dead link）だけを見る一方向の検査。逆向き＝新しい能力（CLI コマンド）が増えたのに、スキル/正本 docs に案内が書かれない（missing link）は機械で捕まらず、verify は緑のまま。実測で data の selectors・tuners・metrics（一覧コマンド）と issue の new（起票）がどのスキル/正本 docs からも到達不能だった（serve スキルに `data monitor` の 1 行が入ったのは作者が覚えていたから＝忘れても検査は落ちない）。
- **対応**：coverage_lint（cli.py 群を ast 解析して `@*.command` を全抽出→スキル/正本 docs での出現を検査・未到達＝error・免除は理由必須の allowlist）を PM_CHECKS に接続し、欠けていた案内を experiment/session スキルに追記して緑化。「部品は使える状態まで」の第 3 要件（スキル/雛形からの案内）の機械化。

## L-015 「同じ経路」は宣言でなく実測で確かめる（公式フックの走査対象が CI では空になりうる）
- **状態**：記録のみ（T-0100 で対処済み。同型の執行点を足すとき＝T-0101〜T-0103 の参照用）。
- **要点**：gitleaks の公式 pre-commit フックの entry は `gitleaks git --staged`＝**ステージ差分だけ**を走査する。CI のクリーンチェックアウト（差分ゼロ）で `pre-commit run gitleaks --all-files` を叩くと、緑だが**何も走査していない**（実測：ツリーに鍵を置いても Passed）。「ローカルと CI が同じ経路」はフック id の一致だけでは成立しない。
- **対応**：entry を作業ツリー全走査（`gitleaks dir .`＝実測 0.1 秒）に上書きし、ローカル・CI とも同じ走査にした。ドットファイル（`.env` 含む）は走査される（実測：`.env`/`.env.probe`/`.probedir/key.txt` すべて検出）。`.venv` 等がスキップされるのは gitleaks 既定の path allowlist による別機序で、ドット始まりだからではない（当初コメントの「ドット始まりは対象外」は誤り＝レビュー N-1 で訂正）。第二候補 detect-secrets は実測で results/ のデータ fingerprint（sha256 の内容ハッシュ）を偽陽性 7 件検出したため不採用。選定は両方とも**偽の鍵を仕込んだ検出デモ**で確かめた。
- **判断**：ガードレールの執行点を足すときは、(1) 止まるべき入力で本当に落ちる、(2) クリーンな状態で本当に通る、の両方を実測してから配線する（vacuous pass は fail-open と同じ）。配線の常在検査は tests/test_guardrails.py の型（ポリシー定数＋データ駆動）をコピーする。**走査モード自体もポリシー定数にして検査する**（`SECRETS_HOOK_ENTRY_PREFIX`＝entry が上流既定に戻ったら赤くする）：id 一致だけの配線テストは entry を消す変異で空振りに退行しても緑のまま通った（レビュー B-1・実測変異で確認）。
- **運用の注意（N-3）**：dir 走査は追跡外・ステージ外のファイルの鍵形文字列でもコミットを止める（想定外の driver は `.gitleaksignore`＝fingerprint 単位・理由必須で逃がす）。
- **settings の接頭辞 deny の限界（N-2）**：Claude Code の `Bash(...:*)` は**語境界つき**接頭辞一致なので、`git clean -f:*` は結合形 `clean -fd`/`-df`/`--force` を捕まえない（`-f` 直後が文字＝境界違反）。最頻の破壊形 `clean -fd` を素通しするため結合形も明示列挙した。フラグ後置（`git push origin --force`）は接頭辞一致の外＝hooks/sandbox の領分として T-0101 以降へ回す（settings だけでは覆えない）。

## L-016 依存監査は全部入り（--all-extras）で行う（部分監査は死角）
- **状態**：記録のみ（T-0102 で対処済み）。
- **要点**：エージェントが自律的に extra を足す運用では、入れている extra だけの監査は「まだ入れていない extra」の脆弱性を見逃す。CI の audit ジョブは `uv sync --all-extras` で同期したロック済み環境そのものを pip-audit で監査する（blocking・免除は `.pip-audit-ignore`＝理由必須。運用ルールの正本は workflow 内コメント）。

## L-017 自分が作りうる欠陥に検出器を足さない（発生源を塞ぐか、機構を作らない）
- **状態**：ルール化済み（AGENTS「概念に 2 つ目の名前を作らない」＋`Registry(require_source=True)`＋review スキルの列挙手順。T-0177・T-0178）。
- **要点**：造語（出典の無い新語）を verify で止めようとして、禁止語→置換語の表（Vale の substitution・textlint-rule-prh 相当）を提案した。オーナーの却下理由が正しい：「自分でバグを仕組んで機械で見つけるのと同じ」。**検出器は既に作られた不良しか知らない**。禁止語の表は次に作られる新語の第 1 号を必ず通すし、実際 `絶対条件` を登録しても `絶対（宣言した閾値を満たす）` という複合しない形は通る。しかも不良が生まれる工程はそのまま残り、検出器だけが保守対象として増える。
- **対応**：発生源を工程として言語化した。造語の発生は 2 種類しかない。(a) 名前の無い概念に名前を付ける（1 か所に集約できる → `register` で出典なしを `ValueError` にする＝fail closed）。(b) 既にある概念に 2 つ目の名前を作る（散文なので集約できない → 機構を作らず、AGENTS の条文＋**独立レビューの列挙手順**で受ける）。
- **判断**：機構を足す前に「なぜ私はそれを書いたのか」を工程として言語化する。集約できるなら発生源で `ValueError`、できないなら**機構を作らない**。レビューの質問は「気をつける」ではなく**列挙できる形**にする（「この差分で新しく現れた名前を挙げ、それぞれの出典を答えよ」＝差分を見れば有限個に確定し、答えが検証可能）。何を止められないかは正直に申告する（`require_source` は書き忘れを不可能にするだけで、出典の中身の真偽は機械には分からない）。

## L-018 characterization テストは、写した先が欠陥ならその欠陥を「仕様」として固定する
- **状態**：記録のみ（T-0170 で作り、T-0176 で欠陥に気づいて挙動を変えた）。
- **要点**：判定ロジックを 2 か所から中核へ抽出する前に、挙動を写し取るテスト（characterization test）を置いた。抽出の等価性を機械的に示せた点では成功した。しかし写した挙動の 1 つ「閾値を課さなければ NaN でも初回昇格できる」は**欠陥**で、テストはそれを守ってしまった。独立レビューが `gates.py` の docstring（「発散したモデルが champion に上がらない」）との矛盾として見つけた。
- **対応**：欠陥を明示した作業単位（T-0176）を立てたうえで挙動を変え、テストも書き換えた。テストの書き換えは「挙動を変えたのに緑にするため」ではないことを、作業単位と `git status`（characterization ファイルが差分に現れないこと）で示す。
- **判断**：characterization テストは**現状の写し**であって仕様ではない。写経が終わったら「写した性質のうち、望ましくないものはどれか」を必ず 1 度問う。とくに **docstring が主張していることと、テストが固定した挙動が一致するか**を突き合わせる（今回はそこが唯一の手掛かりだった）。

## L-019 受け入れ基準に「自分の書いたものを自分で grep する」と書かない
- **状態**：記録のみ（T-0172 の失敗。T-0178 で是正）。
- **要点**：造語を標準用語へ置き換える作業で、受け入れ基準を `grep -rn 関門 が 0 件` と書いた。0 件になったので完了とした。実際には同じ意味の言い換え（`絶対条件`・`相対条件`、さらに複合語ですらない `絶対（…）と相対（…）`）が 10 か所残っていた。**探す語を決めたのは、その語を書いた本人**なので、本人が思い付かなかった形は永久に見つからない。
- **判断**：受け入れ基準は「自分が知っている形を自分で探す」ではなく、**構成から導ける事実**か、**別の立場が確かめられる質問**にする。前者の例：「`profiles = []` の複製で verify が緑」。後者の例：「この差分で新しく現れた名前と、その出典」。自分の記憶を検索対象にした基準は、検証ではなく確認バイアスになる。

## L-020 計画も独立に検証する（「実測で確認済み」と書いた本人が、実測していないことがある）
- **状態**：記録のみ（この検証で 3 つの根拠が崩れ、EP-27 の残り計画・EP-29・EP-30 を書き直した）。
- **要点**：エピックの計画に「実測で確認済み」と明記された 8 項目を、実装していない立場から検証し直した。うち 3 つが誤り。(a)「分割器だけが唯一、拡張口の無い軸」＝偽（反例が 2 つ実在し、片方は同じリポジトリの別の計画文が自認していた）。(b)「loops を中核へ」の台帳は自己申告制で、その案自身が別の箇所で退けた論拠（「入口の無いカタログは嘘の入口になる」）に矛盾していた。(c)「neuralforecast は ray 依存で 3.14 不可」＝既に古い（ray に cp314 wheel が出ていた）。一方で、本当に「実測で確認済み」だった主張（`champion()` が 2 ファイルで文字単位同一・`notes.yaml` 1 つで champion が別版になる・`profiles = []` の複製で収集時に 44 errors）は、独立の再現でも真だった。
- **判断**：レビューの対象は差分（作ったもの）だけではない。**まだ作っていないもの＝計画**にも、作る側と確かめる側の分離を効かせる。とくに「実測で確認済み」「再現済み」と書かれた主張は、書いた本人が確かめたという申告にすぎないので、着手前に別の立場が再現する。依存ライブラリの可否は**日付つきの事実**なので、計画に書いた時点で古くなり始める（着手時に測り直す）。

## L-021 自己申告の台帳は、検出器の別名である
- **状態**：ルール化済み（L-017 の系。T-0184 の「やらないこと」に落とした）。
- **要点**：「止め方の宣言が無いループを verify で失敗にする」ために、各プロファイルが自分のループを申告する台帳（`Profile.loops`）を作ろうとした。これは L-017 の禁じた形そのものだった。**申告し忘れたループは台帳に載らないので、検査に見えない**。第 1 号を必ず通す点で、禁止語の一覧と同型である。
- **対応**：発生源が構文で列挙できるものだけを検査した。定期実行の workflow は `on.schedule` という印を必ず持つので、「`on.schedule` があるなら停止条件の宣言が要る」は書き忘れを不可能にする（`Registry(require_source=True)` と同じ fail closed）。プロセス内の反復には印が無いので検査を作らない。そもそも `range(2, 11)` や `n_trials` で構造的に停止するので、宣言も要らなかった。
- **判断**：検査を設計するとき「対象の集合を、誰がどうやって作るのか」を先に問う。**答えが「書く人が申告する」なら、それは検出器**（申告漏れを見逃す）。**答えが「構文・型・登録の呼び出しから機械的に導ける」なら、それは発生源の封鎖**（書き忘れが不可能になる）。この 2 つは似た顔で現れる。

## L-022 「塞いだ」は、たいてい「自分が思いついた形を塞いだ」でしかない（禁止の列挙でなく、許可の列挙にする）
- **状態**：ルール化の途中（T-0209 で allowlist へ移行中）。
- **要点**：`checks.toml` の空洞化を塞ぐつもりで、3 つの不変条件（未登録マーカー・ruff/mypy の存在・層の被覆）を課した。実装者も呼び出し元も、3 通りの壊し方を実測して「塞がった」と結論した。独立レビューが**別の 5 通り**を実測で通した：`-m "unit and integration and e2e"`（積が空集合＝0 件収集 → exit 5 → 合格）・`-k zzz_never_match` の追加・`--collect-only` の追加・`--ignore=tests` の追加・`["ruff","--version"]` への骨抜き。とくに 1 つ目は「全層を回すつもりで OR でなく AND を書く」だけなので、綴り違いと同じ**悪意ゼロで踏める**事故である。
- **なぜ起きたか**：塞ぐ形（禁止の列挙＝denylist）は、**塞ぐ人が思いついた形しか知らない**。これは L-019（自分の書いたものを自分で grep する受け入れ基準）と L-017（既に作られた不良しか知らない検出器）の第 3 の顔で、対象が「文字列」でも「不良」でもなく「壊し方」になっただけ。
- **判断**：**許すものを列挙する（allowlist）**。pytest に許す引数は `-q` と `-m <式>` だけ、`ruff`・`mypy` は許す argv の集合だけ、と定めれば、**次の書き方も既定で止まる**（fail closed）。「何を走らせてよいか」を固定しても、「どの段階でどれを走らせるか」の自由は残せる（複製先の調整余地を殺さない）。
- **書き方の規律**：塞いだと書くときは「**何を保証し、何を保証しないか**」を書く。「fail open を塞ぐ」ではなく「列挙した 3 経路を塞ぐ」と書いてあれば、レビューの手掛かりになった。

## L-023 テストがフックの「複製」を検証していたら、本体を壊しても緑のまま通る
- **状態**：ルール化の途中（T-0210 で本体へ委譲＋実フックの end-to-end テストへ移行中）。
- **要点**：`slow` マーカーに ISS 参照を必須化したとき、テストは `tests/conftest.py` の収集フックの抽出ロジックを**テスト側に複製**して検証していた（`_extract_skip_markers`）。独立レビューが conftest の抽出を壊すミューテーションを実測したところ、**911 テストが緑のまま**通り、ISS 参照の無い `slow` が素通りで実行された。呼び出し元（私）は実物を叩いて「フックは効いている」ことを確認していたが、**それを守るテストが無い**ので、次の変更で黙って壊れる状態だった。

## L-025 層の再編は「観測された事故」を動機にする（配置の基準は消費者数でなく、別々に持つと事故になるか）
- **状態**：ルール化済み（T-0208 の投資判断としてこの基準を採用。大掛かりな再編そのものは着手しない）。
- **要点**：EP-36 の設計記録は core の 2 層分離・`serve` を `ds` の段階へ格下げ・`ops` プロファイルの解散・
  `leaderboard`／`eval.passes` の中核昇格を提案していた。着手前に成果物の正しさへの寄与を実測で問うと、どれも
  **観測された事故がゼロ**で、動くコードを設計の美しさのために大きく書き換える churn だった。唯一具体だった
  「`serve` が私有関数 `ds.cv._predict` に越境する」も、実際には `_predict` が 6 つのテストファイルで参照
  オラクルとして使われる事実上の公開契約で、`serve` の境界はテスト（serve の出力＝`cv._predict` 直呼び）で
  既に守られていた＝黙って壊れる経路ではない。改名は 11 ファイル・30 か所超の見た目だけの churn になる。
- **なぜ記録するか**：この基準は次の配置判断で効く。**「消費者が 2 つ以上なら core へ」は昇格タイミングの
  経験則であって配置の基準ではない**。配置の基準は「2 つのプロファイルが別々に持つと、観測可能な事故

  重複のまま）は原理違反ではなく、動機の無い再編を避けた正しい倹約である。
- **判断**：**動機（観測された事故）の無い構造再編はしない**。手段の語彙（層・対等・段階）で目的を書くと再編が
  中心に見えるが、目的（案件を重ねるほど強くなる・黙って間違わない）には寄与しない。再編の指摘は記録として
  残し、実際に事故が観測された時点で、その事故を動機に最小の再配置をする。

## L-024 `ruff format`（この環境の 0.15.20）は `except (A, B):` を Python2 構文へ壊す
- **状態**：回避策で対処済み（本体は `except A:` / `except B:` の 2 節に分割）。検出の機械化は候補（下記）。
- **要点**：`uv run ruff format`（**書き込みモード**）が、`as` の付かない複数例外の `except (A, B):` から必須の括弧を剥がし、`except A, B:`（Python2 構文＝Python3 では **SyntaxError**）に書き換える。書き換えられたファイルは import できず、テストが丸ごと落ちる。`except (A, B) as exc:`（`as` 束縛あり）は壊れない（現に `onnx_format.py`・`experiment.py` の 2 か所は無事）。`ruff format --check`（読み取り専用。verify が使う）は壊さないが、`except (A, B):` を「未整形」と判定するので、その形はそもそも verify を通らない。
- **効き方**：これは複数のサブエージェントが「valid なコードを書いたのに verify で落ちる」と失敗し続けた真因の 1 つ。書いた本人は気づけない（自分が書いた `except (A, B):` が、format 実行後に別物へ化ける）。
- **回避**：`as` の付かない複数例外は **2 つの `except` 節に分ける**（`except A: ...` と `except B: ...`）。この形は ruff の正準形なので `--check` も通り、書き込み format でも不変。1 例外なら括弧を付けない。
- **機械化の候補**：pin された ruff に対し、`except (A, B):` の canary を書き込み format にかけて「valid なまま残るか」を検査するテスト（実在するツールのバグを (b) で捕まえる）。未実装。
