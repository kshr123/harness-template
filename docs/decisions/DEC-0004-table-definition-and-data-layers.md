# DEC-0004 テーブル定義の正本は宣言的なYAML、データは層×scope×roleで整理し、物理は抽象で吸収する

## 状況（何を決める必要があったか）
生データが必ずしも綺麗でなく加工が入るため、データの構造・意味の管理（テーブル定義）と、置き場（ローカル・DB/DWH・S3）が
変わっても同じ進め方になる仕組みが必要だった。

## 検討した選択肢
- テーブル定義の正本を、検証コード（pandera）にするか、宣言的なYAMLにするか。
- データの分類を、加工の段数で細かく分けるか、保存の規律で少数の層に絞るか。実験ごとの扱いを層にするか別の軸にするか。
- 物理の置き場（ローカル／DWH／S3）を、コードに直書きするか、抽象で吸収するか。

## 決定と理由
テーブル定義の正本は宣言的なYAML（`docs/data/<id>.yaml`、1テーブル1ファイル）とし、検証の実行器はそこから組み立てる
（読むだけで分かり、Excel定義の取り込みや専用カタログへの書き出しも「変換」になる）。保存の入口を一つにし、定義に照らして
検証したデータだけを書く（保存＝検証済みだけ）。

データは3つの直交する軸で整理する：層（raw／processed／split。分ける基準は保存の規律の違い）・scope（共有か実験ごとか）・
role（人が探すための分類。物理位置に影響しない）。特徴量は processed の一種、モデルは列を持たないため層にせず同じ原則で並行管理する。
実験ごとの産物は実験の scope に置き、共有の processed が膨れないようにする。

物理の置き場は Storage 抽象（位置解決と読み書きだけ）で吸収し、検証・系譜・マニフェストは backend の外に置く。これにより
ローカル・DWH・S3 のどれでも save／load の意味が変わらない。置き場は `.harness/config.toml` の URI で切り替え、層ごとに上書きできる。
版は二段の指紋（実体の指紋＋テーブル版）で持ち、パーティション追記と任意時点の再現を両立させる。

## 影響（良い点・悪い点・これからやること）
- 良い点：置き場が変わっても同じ進め方になり、生の実態を記述しつつ加工後に制約を課せる。分割の固定・特徴量の重複防止が機械化される。
- 悪い点：DWHの内部変換ではバイト単位の指紋が取れず、代替識別になり再現の強さが一段落ちる（マニフェストに明記する）。
- これからやること：実行器は当面 polars で実装（正本から導出）。より本格的な検証が要る案件は同じ正本から pandera 等へ差し替える。
  S3・DWH のアダプタ、`data-check`・`data-draft`・`data-docs` は後続で足す。
