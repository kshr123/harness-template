# DEC-0001 作業単位を木構造（意味のある1まとまり＝1ディレクトリ）で持つ

## 状況（何を決める必要があったか）
作業（タスク・実験）と、その仕様・コード・結果・メモを、どこにどう置くかを決める必要があった。
最初は「タスクは1つのフォルダに平らに並べ、所属するまとまりを frontmatter の欄で指す」形にしていたが、
実際のデータサイエンスでは「大きなまとまりの中に実験があり、その中にさらに細かい作業がある」という
入れ子の粒度があり、また「そのまとまりのものが別々の場所に散らばる」使いにくさがあった。

## 検討した選択肢
- 種類ごとに別フォルダ（タスクはここ、結果はここ、テストはここ）に平らに置く。
- 意味のある1まとまりを1ディレクトリにし、その中に一式を同居させ、まとまりを入れ子にできるようにする。

## 決定と理由
後者を採る。意味のある1まとまり＝1ディレクトリとし、説明・仕様・コード・結果・メモを同居させる。
まとまりは入れ子にでき、親は「置き場所のフォルダ」で表す（所属を指す欄は持たない）。
理由：人が「この作業のもの一式」を1か所で見られる。入れ子の粒度を自然に表せる。
親がフォルダなので「存在しない親を指す」誤りが起きない。
一方で、全体像と進捗は集約が目的なので、木を集計した一覧として別に自動生成する。

## 影響（良い点・悪い点・これからやること）
- 良い点：人にとって分かりやすい。入れ子に対応。結果が単位と一緒に残り、再現・引き渡しがしやすい。
- 悪い点：木をたどる集計処理が必要になる（実装済み：`uv run status`）。
- これからやること：軽い作業はファイル1つ、中身のある作業はフォルダ、という使い分けを規約に明記する（AGENTS.md に記載済み）。
