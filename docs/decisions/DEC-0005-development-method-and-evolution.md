# DEC-0005 開発の進め方（全体→詳細）と、それ自体が進化する仕組みを正本化する

## 状況（何を決める必要があったか）
この基盤は今後あらゆる開発・運用に使い、似た思想で作り続ける。進め方の既定（着手順）と、
気づきが一度きりで終わらず durable な資産（機械検査・抽象・スキル・規約）へ積み上がる仕組みを、
場当たりでなく明文化する必要があった。既に芽（harvest スキル・learnings の「設計への反映」欄・
DEC・pm.lint 等の機械検査）はあるが、束ねる正本と昇格の流れが無かった。

## 検討した選択肢
- A：進め方を AGENTS.md に全部書き込む。→ AGENTS が長くなり「短い決まりの場所」という役割が壊れ、読み込みすぎを招く。
- B：スキルにだけ書く。→ 発火語に依存し、全体像（なぜ・階層）を持てない。
- C：正本を `docs/method.md` に置き、AGENTS には 1 行の決まりだけ、実行手順はスキル、という役割分担にする。

## 決定と理由
C を採る。`docs/method.md` を「開発の進め方と進化の仕組み」の正本とする。要点：
- **標準の進め方＝全体→詳細**（歩く骨組みを先に通し、verify 全成功を保ったまま各部を差し替える）。
- **7 層モデル**（機械検査／抽象／規約／スキル／決定／気づき／記憶）で、各ルールの住処と強制力を定義。正本は 1 か所・参照は下向き・Claude memory はリポの正本にしない。
- **進化のラチェット**：観察→learnings（記録のみ）→2 回目で DEC→落とし先へ昇格→learnings を昇格済みにして棚卸しで削除。昇格時は先に「違反すると失敗する検査」を書く（後戻り防止）。
- **ルール化の原則**：durable なルールは可能な限り機械的な強制点を持つ。持てないものは AGENTS に「（レビュー観点）」と明示。
- **スキル化**：3 手以上・繰り返す・間違えると高い、の 3 条件を満たすものだけ。ML は最小 2 つ（experiment・eda）だけ足す。
理由：層ごとに役割を分け重複を禁じることで、規約の腐敗（同じ文が方々にある・強制されないルールが増える）を防ぎ、
気づきが機械で守られる資産へ確実に積み上がる。AGENTS を短く保つことは「読み込みすぎない」原則とも一致する。

## 影響（良い点・悪い点・これからやること）
- 良い点：進め方が既定として固定され、どの機能・案件も同じ骨組み優先で進む。気づきが昇格の流れに乗り、機械検査で退行が止まる。
- 良い点：AGENTS を短く保てる（全文は method.md）。「機械で守られるルール」と「レビュー頼みのルール」が AGENTS の括弧書きで一望できる。
- 悪い点：層の書き分け（正本 1 か所・参照は下向き）を守る規律が要る。破ると重複が戻る。
- これからやること：AGENTS 原則に「着手は全体→詳細」「進め方も進化させる」を追記済み・plan スキルの分解手順に骨組み優先を追記済み・harvest を 5 手順へ更新済み・learnings に状態欄を追加済み（L-004 を昇格済み→DEC-0002 に）。
  後続タスクで spec_lint に `np.random.seed` 検出、pm.lint に「昇格済み learnings が指す DEC の実在検査」、experiment・eda スキルを足す。
