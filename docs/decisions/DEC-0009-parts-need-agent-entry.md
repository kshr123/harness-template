# DEC-0009 部品は「エージェントが使える入口」まで作って完了

## 状況（何を決める必要があったか）
このプロジェクトの目的は「コードを作ること」でなく「エージェントファーストなプロジェクト開発」——将来の
セッション/エージェントが、スキル・ドキュメント・ルールに導かれ、**毎回コーディングせず用意した部品を
組み合わせて開発できる**土台を作ること。ところが実際の進め方は「部品を実装→設計(DESIGN)→決定(DEC)→
テスト→コミット」までは回るが、**その部品を『エージェントが発見して使う入口』（一覧コマンド・スキル・雛形）
を作る工程が欠けて**いた。実害が 2 回出た：L-007（部品があるのに手書きで再発明）と、E-0001 の雛形が
`build_estimator` を使わず手書き if 分岐だった（コピーすると「部品を使わない実験」を再生産）。＝再コーディング
の発生は 2 回目で、既定「2 回目で昇格」（DEC-0005）の適用。

## 検討した選択肢
- A：入口作り（一覧・スキル・雛形）を別タスクにする。→ 入口だけ永遠に積み残る（今回の実失敗そのもの）。
- B：**完了条件に入口を含める**（部品は入口まで作って初めて done）。

## 決定と理由
B を採る。「再利用する部品は、エージェントが元コードを読まずに使えて初めて done」。3 条件：
(1) **引ける**＝機械可読カタログ（レジストリ）に登録し一覧コマンドに載る。設計時に config へ書ける種は
`uv run data blocks`/`data encoders`/`data models`、既にある実体は `data list`（テーブル）/`data saved`（保存済みモデル）。(2) **分かる**＝docstring に「何をするか・config での書き方」がある。
(3) **導かれる**＝該当スキルか雛形がそこを指す。正本は機械可読カタログ（コードと同居して腐らない）で、一覧は
そこから生成し、スキルは一覧へ導くだけ（散文の使い方ガイドは作らない＝腐る・二重管理）。
機械化できる部分（レジストリ項目に説明文があるか）は pytest（test_catalog.py）で検査し、スキルの導線は
AGENTS の「レビュー観点」に置く（method.md D の作法）。

## 影響（良い点・悪い点・これからやること）
- 良い点：作った部品が同じタスクで「使われる状態」になる。エージェントが `data blocks`/`data encoders` →
  config → build_estimator の型に、コードを読まず・書かず着地できる。
- 良い点：雛形（E-0001）を verify の e2e が毎回実行＝腐らない正本にした（`.harness/templates/` 別置き＝
  誰も実行せず腐る、を避ける）。
- 悪い点：部品タスクに入口更新の手間が乗る（が、積み残りコスト＝再発明より安い）。
- これからやること（実施済み）：`uv run data blocks`/`data encoders`＋説明文必須テスト（T-0021）／E-0001 の
  雛形化（T-0022）／experiment・features スキル新設・DoD/AGENTS/method 追記（T-0023）。harvest に「入口の
  無い部品が無いか」の点検を追加。関連 [[DEC-0005]] [[DEC-0008]]。
