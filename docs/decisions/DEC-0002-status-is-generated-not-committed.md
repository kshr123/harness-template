# DEC-0002 STATUS.md は生成物として扱う（コミットせず、その都度作り直す）

## 状況（何を決める必要があったか）
進捗一覧（`STATUS.md`）は `work/` の作業単位の木を集計した生成物である。当初はこれをリポジトリにコミットし、
「生成物とソース（`work/`）が一致しているか」をコミット前フックと CI（`uv run status --check`）で突き合わせていた。
その結果、`work/` を変えたら毎回 `uv run status` で作り直さないと検証が落ちる、という摩擦が繰り返し起きた
（docs/learnings.md の該当項目）。これは「人が張り付かず、仕組みで品質を担保する」という開発基盤の狙いに反するノイズだった。

## 検討した選択肢
- A：コミットし続け、一致をゲートで強制する（従来）。→ 生成し忘れで検証が落ちる摩擦が残る。
- B：コミットするが、コミット前フックで自動再生成してステージする。→ コミットが書き換わり分かりにくい。
- C：生成物なのでコミットしない（`.gitignore`）。見たいときに `uv run status` で作り直す。一致ゲートは置かない。

## 決定と理由
C を採る。`STATUS.md` は追跡せず（`.gitignore`）、`uv run status` で随時作り直す。生成物とソースの一致を突き合わせる
検査（コミット前フック `harness-status`・CI の `status --check`・`checks.py` の一致確認）はすべて撤去した。
理由：ソースは常に `work/` の木であり、一覧はそこから機械的に導ける。生成物を版管理してソースと同期させる仕掛けは、
「生成し忘れで落ちる」という一群の失敗を生むだけで、正しさには寄与しない。撤去することで摩擦を根本からなくせる。

## 影響（良い点・悪い点・これからやること）
- 良い点：`work/` を編集しても「STATUS を作り直し忘れて検証が落ちる」ことがなくなる。検証がタスクの実体だけを見る。
- 良い点：進捗に加えて「人の判断待ち」（承認待ち・止まっている・未解決の [要確認]）を `uv run status` が同じ一覧に集約する。
- 悪い点：リポジトリを開いただけでは最新の進捗が見えない（`uv run status` を 1 回走らせる必要がある）。
- これからやること：`status --check` サブコマンドは撤去済み。AGENTS.md・設計文書の記述もこの方針に合わせて更新する。
