# DEC-0016 導線カバレッジ検査を機械化する（coverage_lint＝DEC-0009 の第 3 要件を強制）

## 状況（何を決める必要があったか）
DEC-0009「部品は入口まで作って完了」の DoD 3 要件のうち、①レジストリ登録②docstring は機械検査があるが、
③「スキル/雛形からの導線」は未機械化＝書き忘れても `uv run verify` は緑のままだった。既存の doclint は
**一方向**（書いた参照が実在するか＝dead link）しか見ないため、逆向き＝**新しい能力（CLI コマンド）が
増えたのに導線が作られない（missing link）**は捕まらない。実測で `data selectors`・`data tuners`・
`data metrics`・`issue new` がどのスキル/正本 docs からも到達不能だった（EP-19・L-013）。
「スキルとドキュメントが開発のたびに進化しているか」を人間の記憶でなく機械で担保する方法を決める必要があった。

## 検討した選択肢
- A：レビュー観点のまま（DEC-0009 の現状）：導線の有無は独立レビューが見る。
- B：**coverage_lint を core に追加**：`src/harness/**/cli.py` を ast で解析して `@<app>.command("name")` を
  全抽出し、各コマンドのトークン（`data selectors` 等）が探索コーパス（`.claude/skills/**/*.md`＋AGENTS.md＋
  README.md＋docs 直下の *.md）に 1 回以上現れるかを検査。未到達＝error として PM_CHECKS（verify）に接続。
  免除は理由必須の allowlist（`_EXEMPT`）だけ。
- C：Registry.catalog を舐めて部品単位で導線を検査する（コマンドでなく部品の粒度）。
- D：DEC→AGENTS の昇格反映やスキルの意味的鮮度まで自動検査する。

## 決定と理由
**B を採用**。理由：
- 実測で穴が再現している（A のレビュー観点だけでは、覚えていた人がいるかどうかに依存する＝L-013）。
- CLI コマンドは「エージェントが部品を発見する入口」の代表で、`@*.command` の全抽出は正本（cli.py）から
  機械的に導出できる＝判定基準が明確で偽陽性が少ない。cli.py は import せず**テキスト/AST として読む**
  （doclint と同じ作法）ので、core がプロファイルを import しない境界（DEC-0004）を壊さない。stdlib のみ。
- 免除（例：`data lint`＝verify が毎回自動で呼ぶ内部入口）は allowlist に**理由必須**で明示する。missing を
  error にする検査なので、サイレントな見逃し（暗黙の免除）を作らない（理由が空は ValueError＝fail closed）。
- C は B で代替できる（コマンド一覧はレジストリから生成される＝入口の検査で足りる。二重の仕組みを持たない）。
  D は過検査（判定基準が無い・偽陽性が多い＝EP-19 の取り込み判断で不採用）。

## 影響（良い点・悪い点・これからやること）
- 良い点：新しい CLI コマンドの導線忘れが verify で必ず落ちる＝「ドキュメントが進化しているか不安」への
  機械的な答え。AGENTS.md の規約（新しい CLI コマンドはスキル/正本 docs への導線が必須）に検査点が付いた。
- 悪い点：部分文字列の出現で「到達可能」とみなすため、導線の質（説明が十分か）までは見ない。→ 緩和：
  質は独立レビューの観点のまま残す（機械は有無だけを保証する）。
- これからやること：プロファイル×スキルの粗い対応検査・免除リストの棚卸し（harvest）を、必要が出たら
  DEC-0012 の基準で追加する。関連 [[DEC-0004]] [[DEC-0009]] [[DEC-0012]]。
