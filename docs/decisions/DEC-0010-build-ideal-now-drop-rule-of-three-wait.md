# DEC-0010 理想形を今作る：Rule of Three の「待ち」をオーナー判断で解除する

## 状況（何を決める必要があったか）
`docs/structure-review-2026-07.md` と DEC-0005 の運用として、汎用化・部品化は「同じ必要が 3 回出る（2 つ目のドメインが
出る）まで待つ」＝Rule of Three で先送りしてきた。2026-07-05 の ds レビューでオーナーが「現段階で理想的なプロジェクトを
作る。回数に関係なく、部品として作っておくと良いものは全部作る。必要なら仕組みを抜本的に変えてよい」と明示した。
この方針転換を記録し、以後の判断基準を切り替える必要があった。

## 検討した選択肢
- **A：Rule of Three を維持**（2 つ目のドメインまで構造刷新・部品追加を待つ）。
- **B：待ちを解除し、良い部品・良い継ぎ目を今すべて作る**（ただし本当に優れた核は温存する）。

## 決定と理由
**B を採用**。理由：(1) このリポ自体がテンプレート＝「理想形の土台」を配ることが目的で、複製先の質は土台の完成度で決まる。
(2) 先送りの根拠が既に崩れている実例がある（`docs/template-copy.md` が案件ごとに `src/harness/` のコア編集を要求＝
「src は触らない」宣言と自己矛盾／`cli.py` の 2/3 が DS コードで core↔ds 境界が決壊）。仮定の第 2 ドメインではなく
「今日の実害」なので前倒しは novelty でなく整合の回復。(3) 追加する部品は大半が sklearn 等の薄い包み（DEC-0006/0008 準拠）で
保守負債が小さい。

**ただし「理想＝全書き換え」ではない**。genuinely excellent な核は温存する（DEC-0010 の適用外）：run_cv の clone-per-fold と
oof_mask／fold_indices の 1:1 検査／pm.py の木と lint／段階×マーカー検証と未マーク失敗ガード／STATUS 非コミット
（DEC-0002）／課題を木の外に置く設計（DEC-0003）／e2e が実雛形を叩く方式／plan=outline を咎めない設計。

## 影響（良い点・悪い点・これからやること）
- 良い点：DS ハーネスとしての完成度が上がり、複製先が「部品を再コーディングせず使える」度合いが増す。core↔ds の境界が
  実装でも一致し、非 DS 複製が「config 1 行」で済む。
- 悪い点：一度に触る面積が広い＝退行リスク。→ 緩和策：`docs/ideal-build-plan-2026-07-05.md` の波（EP-13..16）で 1 PR ずつ、
  テスト先書き＋独立レビュー＋`uv run verify` 緑を各タスクで守る（DEC-0009 の完了条件は据え置き）。
- これからやること：ISS-0006〜0011 を「待ち」から本計画のタスクへ移す。保存 4 作法・検証方針は Wave 2 完了時に
  DEC-0011 として別途記録する。この判断が過剰だったと後で分かれば、本 DEC を superseded にして揺り戻す。
