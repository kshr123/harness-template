# DEC-0014 このハーネスの対象は ML ライフサイクル全体（学習は入口であって境界ではない）

## 状況（何を決める必要があったか）
DEC-0013 とその実装（EP-17）で、配信・運用の一部（A/B・shadow ルーティング・prediction cache・edge・
circuit breaker・load test・async キュー・gRPC・クラウド固有 S3/GCS・model_db）を「将来に回す」と決めた。
そのとき理由づけを **「配信基盤側の関心＝学習ハーネスの外」** と書いた（DEC-0013 の「将来に回す」節・
EP-17 item.md の「やらないこと」）。オーナー指摘：**この線引きは根本から誤り**。本ハーネスは「学習“から”
始める」だけで、**対象が学習に限られるわけではない**。配信も運用もこのハーネスの対象であり、上記の後回し項目は
「対象外」ではなく「まだ作っていない（順番の問題）」。この根の勘違いを正本として直す必要があった。

## 検討した選択肢
- A：ハーネスの範囲を「学習・実験・レジストリ」に限定し、配信/運用は別プロダクトの関心とする（従来の暗黙の線引き）。
- B：**ハーネスの範囲は ML ライフサイクル全体**（データ→特徴→学習→評価→**配信→監視→運用→再学習**）とし、
  「学習」はその入口・最初に作った層にすぎないと位置づける。未実装の配信/運用は「対象外」でなく「未着手の将来プロファイル」。

## 決定と理由
**B を採用**。理由：
- charter の思想＝「この基盤自身が最初の案件」。ML の価値は配信・運用まで届いて初めて出る。学習だけで閉じるのは
  ライフサイクルの一部で止めること＝基盤の目的に反する。
- プロファイル境界（DEC-0004）は既に「中核＋差し替え可能な層」を許す。配信（`harness.serve`）・運用（将来 `harness.ops` 等）は
  この機構の**正当な拡張**であって例外ではない。「学習ハーネス」という語が範囲を狭く錯覚させていただけ。
- 線引きの基準は **「学習の対象/外」ではなく「今理想形として作れるか（DEC-0010）× 一般性（DEC-0012）× 実行基盤は
  利用者環境に委ねテンプレ＋lint＋スキルで担保できるか（DEC-0013 の思想）」**。この基準で now/soon/later を決める。

**運用ルール（この DEC 以降の言い回しの正本）**：
- 後回し項目を「学習ハーネスの対象外」「配信基盤側の関心＝外」と書かない。書くなら「未着手の将来プロファイル
  （順序の問題）」と明記し、この DEC を参照する。
- 各プロファイル（serve・将来の ops 等）は中核・既存プロファイルを壊さない（境界は DEC-0004 のまま）。
- 実行時の重い基盤（k8s 実物・クラウド課金・常駐ルーティング）は利用者環境に委ね、ハーネスは
  **抽象（config の差し替え軸）＋テンプレート＋構造 lint＋スキルの導線**で担保する（deploy_lint と同じ思想）。

## 影響（良い点・悪い点・これからやること）
- 良い点：範囲の錯覚を除き、配信/運用の作り込みを「対象外なので後回し」でなく「順番で未着手」として堂々と計画できる。
  now/soon/later の判断が DEC-0010/0012/0013 の既存基準に接続する（新しい歯止めを増やさない）。
- 悪い点：範囲が広く見え、YAGNI（作りすぎ）の誘惑が増える。→ 緩和：判断基準は上記のとおり厳密（今理想形×一般性×
  委譲可能）。「対象だから全部作る」ではない。作りすぎは method.md D 節・DEC-0012 の一般性判断で止める。
- これからやること：DEC-0013 の「将来に回す」節と EP-17 item.md の「やらないこと」の**言い回しを本 DEC の語で修正**
  （中身の順序は変えない）。配信/運用の洗い出し・整理を行い、now の項目を新エピックとして計画する。
  関連 [[DEC-0004]] [[DEC-0010]] [[DEC-0012]] [[DEC-0013]]。
