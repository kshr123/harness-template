# DEC-0019 ドキュメント標準：Diátaxis 分類・標準用語・可視の導入・発見可能・簡潔（doc_standards で機械化）

## 状況（何を決める必要があったか）
現行ドキュメントは「エージェントには読めるが、人には分かりにくい」（EP-24 の監査）。原因は 4 つ：
(1) 全体像→詳細の順になっていない（いきなり機構の説明に入る）、(2) 人間向けの索引が無く、どこに何の文書が
あるか分からない（孤立文書が生まれる）、(3) 粒度・分割が不適切、(4) 用語が造語（「金メッキ」「関門/門番」
「昇格」の二義など）で、エンジニア・データサイエンティストの一般用語に対応づいていない。
「人が初見で・過不足なく理解できる」文書の標準と、それを守らせ続ける仕組みを決める必要があった。

## 検討した選択肢
- **A：都度レビューで直す（標準を明文化しない）**。書き手の善意頼みで、セッションが替わるたびに退行する。
- **B：外部の文書 lint（Vale）を CI に入れる**。用語・禁止語の検査は強いが、外部バイナリの導入が
  「verify はネットワーク 0・stdlib 中心」の方針（DEC-0015 の検証思想）に合わない。
- **C：業界標準（Diátaxis＋Google スタイル）を正本として明文化し、機械化できる部分だけを stdlib の軽い検査
  `doc_standards`（coverage_lint と同型）に翻案する**。

## 決定と理由
**C を採用**。標準は次の 5 点（各文書の書き手＝人・エージェントの両方が従う）：

1. **構造は [Diátaxis](https://diataxis.fr) の 4 分類**：文書を Tutorial（手を動かして学ぶ）／How-to
   （目的達成の手順）／Reference（事実・契約）／Explanation（なぜ）のどれかとして書き、混ぜない。
   分類は索引 `docs/README.md` の文書地図に載せる。
2. **用語は標準用語**（[Google developer documentation style guide](https://developers.google.com/style/jargon)
   の jargon 規範）：造語・内部用語は避け、使うなら**初出で定義するか `docs/glossary.md` へリンク**する。
   用語集は造語→平易な定義＋標準用語（英/カナ）の対応を持つ。
3. **各正本文書は可視の平易な導入（lede）で始める**：その文書が何で・誰がいつ読むかを、本文の冒頭に
   見える形で書く（HTML コメントに隠さない）。
4. **発見可能**：すべての正本文書は索引 `docs/README.md` から辿れる（孤立文書ゼロ）。日付付きの作業メモは
   正本ではないので `docs/archive/` に置き、索引の対象外とする。
5. **過不足なく簡潔**：読者が目的を果たすのに必要なことだけを書く。同じ内容を 2 か所に書かない
   （正本は 1 か所・他はリンク。`docs/method.md` F 節と同じ規律）。

理由：Diátaxis と Google スタイルは「全体像→詳細・適切な粒度・平易な用語」の業界標準の型であり、
自前の書き方ルールを発明しない（DEC-0006 の思想を文書に適用）。執行は [Vale](https://vale.sh) の
docs-as-code パターン（用語・構造を CI で検査する考え方）を、外部バイナリなしで
`src/harness/doc_standards.py`（stdlib のみ・`uv run verify` の PM_CHECKS に接続）に翻案する。

**機械化する部分と、レビュー観点に残す部分の線引き**（正直な線引き＝検査できると嘘をつかない）：

| 担保 | 内容 |
| --- | --- |
| 機械（doc_standards・T-0130 から） | 孤立検査（`docs/*.md` が索引からリンクされている）／凡例網羅（使われている ID 接頭辞が索引の凡例にある）／用語集整合（`docs/glossary.md` が存在・見出し重複なし・空定義なし） |
| 機械（doc_standards・T-0131/0132 で追加） | 導入（lede）検査（正本文書が可視の平易な導入で始まる）／最悪造語の denylist（用語集に対応の無い造語の使用を止める） |
| レビュー観点（review スキル） | 初見で理解できるか・過不足がないか・Diátaxis 分類として混ざっていないか・導入が実際に平易か（機械は「有無」しか見られない） |

免除は他の lint と同型の**理由必須 allowlist**（`_EXEMPT`・空理由は ValueError）だけとする。

参考：[diataxis.fr](https://diataxis.fr)（構造）／
[developers.google.com/style](https://developers.google.com/style/jargon)（用語）／
[vale.sh](https://vale.sh)（docs-as-code の執行パターン。バイナリは採用せず考え方だけ翻案）。

## 影響（良い点・悪い点・これからやること）
- 良い点：人間の読者が索引→用語集→各文書と迷わず辿れる。文書の腐り（孤立・凡例欠落・用語集不整合）が
  verify で止まり、セッションが替わっても退行しない（ratchet）。
- 悪い点：文書を足す・改名するたびに索引の更新が必要になる（意図した摩擦＝発見可能性の対価）。
  検査できるのは構造だけで、「分かりやすさ」そのものは引き続きレビュー頼み（上の線引きの表が正本）。
- これからやること：T-0131（Reference/プロファイル文書の刷新＋lede 検査の追加）・T-0132（中核ルール文書の
  刷新＋造語 denylist の追加・review スキルへの観点追加）。
