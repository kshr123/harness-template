# DEC-0003 1リポジトリ＝1案件とし、作業単位に調査を加え、課題は別の登録簿にする

## 状況（何を決める必要があったか）
案件レベルの文書・作業・発見された問題の置き場と、作業単位の種類を決める必要があった。当初は
`projects/<案件>/` の下に案件文書を置き、作業単位はエピック・タスク・実験の3種類だけだった。

## 検討した選択肢
- 案件文書を `projects/<案件>/` に置き、複数案件を1リポジトリに同居できるようにする。
- 1リポジトリ＝1案件とし、案件レベルの文書は `docs/`、発見された問題は `issues/` に置く。
- 作業単位に「調査」を足すか、タスクの一種で済ませるか。課題を作業単位の種類にするか、別の登録簿にするか。

## 決定と理由
1リポジトリ＝1案件とし、`projects/<案件>/` の層を廃止する。最上位を寿命と読者で分け、`docs/`（案件レベルの文書）・
`work/`（作業単位の木）・`issues/`（発見された問題）に置く。理由：課題の置き場に GitHub Issues を選べるようにするには
リポジトリと案件が一対一である必要があり、PR・CI・要件連番の一意性もリポジトリ単位で自然に閉じる。開発基盤はテンプレートを
案件ごとに複製して使う。

作業単位は4種類にする：エピック・タスク・調査（investigation）・実験。分ける基準は完了条件・生涯・成果物のいずれかの違い。
調査はタスクと完了条件が違う（テストではなく結論の記録で完了する）ため、タスクの一種にすると検査の例外ができて逃げ道になる。

課題（issue）は作業単位の木の種類にしない。生涯（open→対応中→解決／見送り）が違い、木に入れると進捗率が壊れ、発見時に
置き場を決められない。木の外の登録簿に置き、対処すると決めた時点でタスクか調査に昇格させて木につなぐ。

## 影響（良い点・悪い点・これからやること）
- 良い点：迷わない構成になり、課題の置き場を設定で切り替えられる。発見された問題が記録される受け皿ができる。
- 悪い点：案件をまたぐ共有コードの再利用が一手間になる（テンプレート還流とライブラリ化で解く）。
- これからやること：S3・DWH・GitHub Issues の実アダプタは後続で足す（この時点ではインターフェースを固定し、ローカルのみ実装）。
